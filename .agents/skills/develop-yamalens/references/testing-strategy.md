## 基本原則

- 多数の速いユニットテスト、必要な結合テスト、少数の重要なUIテストというテストピラミッドを使用する。
- 実装の内部構造ではなく、入力に対する観測可能な結果を検証する。
- 1テストで一つの動作を検証し、失敗名だけで壊れた条件と期待結果が分かるようにする。
- 正常系だけでなく、境界値、欠損、キャンセル、権限拒否、低精度、オフライン、古い情報、破損データを扱う。
- テストを通すために本番の安全確認、並行性検査、エラー処理を弱めない。
- プレビュー、モック画面、コンパイル成功だけで動作確認済みとしない。

## テストの種類と責務

| 種類 | 保証するもの | 保証しないもの |
| --- | --- | --- |
| ユニット | 純粋な計算、変換、状態遷移、エラー分類 | Appleフレームワークや保存先との接続 |
| 結合 | Repository、保存、ファイル、変換処理が組み合わさる動作 | 実ネットワークや実センサーの品質 |
| UI操作 | 利用者が主要な操作を完了できること | 候補算出の全境界値や見た目の細部 |
| 性能 | 固定条件での処理時間、メモリ等の回帰 | 全端末・全環境での絶対性能 |
| 実機 | 権限、カメラ、センサー、外部サービスとの実接続 | 丹沢の各地点で候補が有用であること |
| 現地 | 実際の地形・方位・遮蔽物を含む候補の有用性 | コードの全分岐 |

ユニット・結合テストにはSwift Testing、UI操作と性能テストにはXCTest／XCUIAutomationを使用する。外部のテストライブラリは追加しない。

## 変更ごとの必須テスト

| 変更対象 | 最低限必要な確認 |
| --- | --- |
| Domainモデル・計算 | 正常値、境界値、不正値、欠損を扱うユニットテスト |
| 候補順位付け | パラメーター化テスト、固定リプレイ、順位と精度低下理由 |
| ScreenModel | 読み込み、成功、空、失敗、再試行、キャンセル後に古い結果を反映しないこと |
| SwiftData・SQLite | 一時ストアへの保存、再読込、更新、削除、破損・移行失敗 |
| オフラインパック | 検証前に切り替えないこと、中断、容量不足、破損、直前版へのロールバック |
| 天気・変動情報 | 30分・1時間・3時間・60秒再試行の境界、提供元、注意閾値、未取得・更新失敗の変換 |
| 権限・センサー | 許可、拒否、制限、低精度を固定入力で再現したFeatureテスト。実取得は実機確認 |
| SwiftUI画面 | 関係する状態のプレビューまたは状態テスト。重要導線ならUI操作テスト。Liquid Glass変更ではアクセシビリティ設定と実機視認性も確認 |
| バグ修正 | 修正前に失敗し、修正後に成功する最小の回帰テスト |

文言、余白、コメントだけの変更では新規自動テストを必須にしない。ただしアクセシビリティ、意味、操作、状態表示が変わる場合は動作変更として扱う。

## 決定性とテストダブル

- `Date.now`、乱数、UUID、現在地、ネットワーク、実センサー、実ファイル領域をテストから直接使用しない。
- Clock、ID生成、Repository、センサー観測、通信結果、保存先をイニシャライザーで注入する。
- 固定値を返すStub、呼び出しを記録するSpy、小さな実動作を持つFakeを用途に応じて使う。呼び出し順の細部まで過剰に固定しない。
- 非同期テストで一定時間の `sleep` に成功条件を依存させない。完了イベント、制御可能なClock、継続、テスト用Fakeで同期する。
- Swift Testingは並列実行を前提とし、テストごとに状態、データベース、一時ディレクトリを分離する。直列化は共有が避けられない理由を記録した場合だけ使用する。
- 実ネットワークを使うテストを通常の自動テスト群へ含めない。

## Domainと候補算出

- 距離、方位、仰角、角度正規化、画角内判定は、単位と許容誤差を明示する。
- 359度と1度、画角境界の内外、極端な標高差、同一座標、不十分な精度、データ範囲外を含める。
- 候補順位の同点時には、結果が毎回同じになるタイブレーク規則を検証する。
- ズームとレンズの有効画角、手動補正の適用とセッション終了時のリセットを検証する。
- 150km、score 0.35・0.50・0.75、水平精度25m・100m、方位精度10°・25°、垂直精度30m・75m、観測時間の各境界について、直前・一致・直後をパラメーター化して検証する。
- 方位45%、仰角30%、観測品質15%、距離10%の合計とタイブレークが決定的で、無効な高度を0mとして扱わないことを検証する。
- 現地診断ログを匿名化した固定リプレイへ変換し、アルゴリズム変更前後で主要候補と精度低下理由を比較する。
- 数値の完全一致が仕様でない場合は、根拠のある許容誤差または順位・範囲で検証する。

## Featureと画面状態

- ScreenModelは `@MainActor` 上でテストし、公開状態と利用可能な操作を確認する。
- 読み込み中、成功、空、失敗、再試行、オフライン、古い情報、権限拒否、低精度を関係する画面ごとに検証する。
- 画面離脱、検索語変更、再読み込みで前のTaskがキャンセルされ、古い結果が新しい状態を上書きしないことを検証する。
- エラー型の内部文字列ではなく、利用者に示す理由、代替操作、再試行・設定導線の状態を検証する。
- 一時的な失敗、利用者操作待ち、データ不正、機能制限、内部不具合の各分類が、正しい再試行可否とUI状態へ変換されることを検証する。
- カメラや位置情報を拒否しても、一覧、検索、詳細、メモ、お気に入りへ到達できることを検証する。

## Infrastructureと永続化

- SwiftDataはメモリ内またはテスト専用ストア、SQLiteとファイル操作はテストごとの一時ディレクトリを使用する。
- Repositoryの契約を、Fakeだけでなく具象実装に対しても共通ケースで確認する。
- オフラインパックは一時保存、ハッシュ・版・必須データの検証、アトミック切り替え、旧版保持の順序を検証する。
- パックはEd25519署名、既知・未知のkeyID、manifest生バイト、SHA-256、byte数、SQLite整合性、schemaVersion、必須レコードの各失敗を個別に再現し、いずれも旧パックを保持することを検証する。
- パック削除・置換後も `UserMountainState` のメモとお気に入りが残ることを結合テストで確認する。
- WeatherKitやURLSessionの応答は、固定した成功・欠損・失敗データをDomain状態へ変換する部分をテストする。WeatherKit本体の正しさや実サービス到達性は自動テストの対象にしない。
- 固定Clockと待機処理を使い、WeatherKitと小要求の15秒、2秒後1回再試行、60秒の自動更新間隔、パックの無通信30秒・全体2時間を待ち時間なしで検証する。同一要求の集約、キャンセル、再試行対象外のエラーも確認する。
- 気象は取得から30分・1時間・3時間、再試行60秒、12時間評価範囲、予報風速10m/s・15m/s、任意の3時間で5℃低下の各境界を固定Clockと固定予報で検証する。雷・雪・警報が取得不能な場合を「なし」に変換しないことも確認する。
- 前日気象は地点のタイムゾーンにおける暦日境界、対象日一致・不一致、6時間キャッシュの直前・境界・直後、部分欠損、現在・予報だけ成功／前日だけ成功を固定Clockで検証する。欠損を0mm・0cmへ変換しない。
- 駅検索は通信成功、0件、失敗、キャンセル後の古い結果、同名駅、無効座標を検証する。検索語を永続化・ログ出力しないことも確認する。
- 外部地図は、現在地で出発地を省略する場合、登録駅を明示する場合、登録駅なし、Google Maps利用不可、移動手段、無効な目的地の生成結果をユニットテストし、実際に開くことは実機で確認する。
- `SavedDeparturePoint` は1件の登録・置換・削除・再起動後保持、位置権限拒否時の利用、パック削除からの独立を結合テストで確認する。
- パック導入の各ジャーナル状態と異常終了を再現し、`readyToInstall` の再検証、旧パック保持、24時間経過した孤立領域の削除を確認する。
- SwiftDataを開けない場合にストア、WAL、SHMを削除せず、個人データ以外の機能が継続することを確認する。
- manifestの256KiB、ファイル2件、総量1,000,000,000byte、署名64byte、URL 2,048文字、未知のファイル名、絶対パス、`..`、地形タイル131,072byte、offset・length境界を正常・直前・直後の値で検証する。
- SQLiteが読み取り専用・拡張読み込み無効であること、データ由来の文字列がSQLとして実行されないことを確認する。
- 一時ディレクトリでFile Protectionとバックアップ除外属性を確認する。実機のロック中アクセスは実機試験として区別する。
- 診断ログが明示開始前に保存されず、30日・20件の境界、保持指定、個別・全削除、匿名化共有、座標共有の追加確認、一時ファイル24時間削除に従うことを検証する。

## UIとアクセシビリティ

- UI操作テストは、起動→一覧→検索→詳細、お気に入り更新、メモ保存、保存済み情報のオフライン閲覧を優先する。
- 「ここへ行く」sheetで現在地・登録駅を選べる状態、駅未登録、Dynamic Type最大時の長い駅名、VoiceOverの選択状態を検証する。
- 前日サマリーの通常、部分欠損、取得失敗、対象日不一致を現在・予報とは独立した画面状態で検証する。
- 将来通知を実装する変更では、既定OFF、文脈内の権限要求、前日18時、予定変更・削除による更新／取消、拒否後の非通知機能継続を固定NotificationSchedulerで検証する。
- UIテスト用の起動引数または依存注入で固定データと状態を選び、実ネットワークや権限ダイアログの偶然に依存させない。
- UIテスト用の状態切り替えはDebug／テストビルドだけで有効にし、本番ビルドから起動引数等で有効化できないようにする。
- 重要な要素へ安定したAccessibility Identifierを付け、表示文字列や座標だけで要素を探さない。
- 通常、空、失敗、オフライン、古い情報、権限拒否、低精度、Dynamic Type拡大のプレビューを用意する。
- VoiceOverの読み上げ順、ラベル、値、ヒント、色だけに依存しない状態表現は、シミュレーターまたは実機で手動確認も行う。
- Liquid Glassを使用する画面はLight／Darkに加え、「透明度を下げる」「コントラストを上げる」「視差効果を減らす」で情報と操作を確認する。独自ガラス部品はカメラ背景など明暗の異なる固定状態も用意する。
- スクリーンショット比較ライブラリはMVPへ追加しない。見た目の回帰が頻発し、保守コストを上回る効果が確認できた場合に再検討する。

## 実機・現地検証

- iPhone 15 Pro以降で、カメラ権限、位置権限、モーション、真北方位、画角、ズーム、バックグラウンド移行時の停止を確認する。
- WeatherKit認証と取得、外部公式リンク、Apple Maps、利用可能な場合のGoogle Mapsを実機で確認する。
- 丹沢の代表地点では、目視可能な主要ピーク、候補順位、ラベルずれ、低精度表示、手動補正を記録する。
- 実機・現地結果を自動テスト結果と混ぜず、端末、OS、日時、地点区分、パック版、結果、未確認事項を記録する。
- 現地未実施の項目を、シミュレーターや固定リプレイだけで受け入れ完了にしない。

## 性能テスト

- 候補順位付け、地形見通し判定、パック読み込み、検索を性能候補とし、実装後に代表データ量と基準値を記録する。
- デバッグビルドの一度の計測値ではなく、同一条件で反復して回帰を比較する。
- 失敗基準を設定する前に実機または代表シミュレーターでベースラインを取得する。
- カメラ使用中のCPU、メモリ、発熱、電池消費はInstrumentsと実機で確認し、自動ユニットテストだけで判断しない。
- カメラ画面へ独自Liquid Glassを追加・変更した場合は、効果数と `GlassEffectContainer` の構成を記録し、追加前後でフレーム落ちと発熱の回帰を確認する。

## 実行順序と失敗時の扱い

1. 実装中は、変更した型・機能に最も近いユニットテストを実行する。
2. 次に、関係するFeatureとInfrastructureの結合テストを実行する。
3. UI変更または主要導線への影響がある場合は、対象UIテストを実行する。
4. 引き渡し前に、利用可能な全ユニット・結合・UIテストとアプリのビルドを実行する。
5. センサー、カメラ、権限、WeatherKit、外部地図に関係する場合は、必要な実機確認を別に実施または未確認として記録する。

Pull Requestでは `ci-strategy.md` に従い、GitHub Actionsでも同じビルドと自動テストを実行する。CI成功はローカル検証を省略する根拠ではなく、CI未実行・失敗を手元で成功した結果だけで完了扱いにしない。

失敗したテストを削除、無効化、期待値変更だけで通さない。仕様、実装、テストのどれが誤っているかを正本文書と観測結果から判断する。不安定なテストは再実行だけで済ませず、共有状態、時刻、待機、実ネットワーク、実行順序への依存を除去する。

Xcodeプロジェクト作成時は、アプリ、ユニットテスト、UIテストを同じSchemeから実行できる既定のTest Planを一つ用意する。実行時間が問題になるまでは多数のTest Planへ分割せず、開発中は対象テストの選択実行、引き渡し前は全実行とする。

## カバレッジと受け入れ証拠

- 一律のコードカバレッジ率をMVPの合格条件にしない。
- カバレッジは、Domainの未実行分岐、エラー経路、重要な状態遷移を発見するために使用する。
- 新規・変更したDomain動作、安全上重要な分岐、受け入れ条件には、具体的なテストまたは実機・現地証拠を対応付ける。
- 引き渡し時は、実行したコマンド、成功・失敗・未実行、対象環境を示す。「全テスト成功」は実際に全対象を実行した場合だけ記載する。
- 実機、認証情報、丹沢現地が必要で未確認の項目は、残作業として明記する。

## テストデータとプライバシー

- テスト用の山、座標、天気、メモは架空または公開可能な固定データを基本とする。
- 実際のメモ、検索語、継続的な位置履歴、カメラ映像をFixtureへ含めない。
- 現地ログは必要最小限とし、共有前に個人を特定する情報と不要な正確位置を確認する。
- APIキー、WeatherKit認証情報、署名情報をテストコード、Fixture、ログへ保存しない。
- 大容量パックをテストターゲットへ含めず、最小の破損・正常Fixtureを使用する。
