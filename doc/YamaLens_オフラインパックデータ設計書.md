# YamaLens オフラインパックデータ設計書

作成日: 2026-08-26
対象: 丹沢の個人利用MVP／開発用地形比較パック

本書は、オフラインパックの**データ形式・保存単位・現在の収録状況**を説明する設計書である。プロダクトの範囲と安全性は [事前決定事項](YamaLens_事前決定事項.md)、アプリの実装・検証規則は [基本設計書](YamaLens_基本設計書.md)、配布・運用は [オフラインパック設計方針](YamaLens_オフラインパック設計方針.md) を正とする。

## 1. 結論

オフラインパックは、山域ごとの「小さなデータベース」と「地形の標高ファイル」の組である。山を一座ずつ大きなデータとして保存しているわけではない。

```text
丹沢パック
├─ manifest.json      何のパックか、2つの本体ファイルのサイズ・SHA-256
├─ manifest.sig       manifest.json の Ed25519署名
├─ catalog.sqlite     山、別名、施設、出典、地形タイルの索引
└─ terrain.lzfse      256×256セルの圧縮済み標高タイル本体
```

- 利用者に見せる単位は「丹沢山地」のような**山域パック**。
- 山頂は1座ごとのレコード、別名は山頂に紐付くレコード、施設は独立したレコードで持つ。
- 地形は山頂ごとではなく、Webメルカトルの**固定サイズ地形タイル**で持つ。
- `catalog.sqlite` は検索・関連付け・地形ファイルの読込位置を持ち、標高値そのものは `terrain.lzfse` に置く。
- メモ、お気に入り、写真、現在地履歴、天気キャッシュはパック外の端末内保存であり、このデータベースには入れない。

## 2. 現在の丹沢パックに実際に入っているもの

以下は、開発用同梱パック `tanzawa-detailed-v1` の `contentVersion 1.0.1` を直接調査した値である。R2の `1.0.2` は更新導線確認用の同一内容テスト版であり、実データの拡充版ではない。

| 区分 | 現在の収録量 | 内容 |
| --- | ---: | --- |
| パック本体 | 約60MB（57MiB） | ほぼ全量が地形 |
| `catalog.sqlite` | 588KiB | 検索・索引・出典。地形本体は含まない |
| `terrain.lzfse` | 56.7MiB | 圧縮済み地形タイル |
| 山頂 | 17座 | 丹沢の中心6座 + 遠方識別用の周辺候補11座 |
| 山名・別名 | 42件 | 検索用の正規化名を含む |
| 地形タイル | 1,453枚 | 256×256セル単位 |
| 施設（POI） | **0件** | 現行の配布済み詳細パックには未収録 |
| 出典リンク | 1件 | 国土地理院の標高タイル |

### 2.1 山頂の収録範囲

`core` は丹沢として詳細情報を整備する対象、`surroundingCandidate` は丹沢から見える可能性があり、AR候補の取り違えを抑えるための周辺候補である。周辺候補を入れても、その山域の施設・詳細情報まで対応済みという意味にはしない。

| 区分 | 座数 | 現在の山 |
| --- | ---: | --- |
| `core` | 6 | 蛭ヶ岳、檜洞丸、丹沢山、塔ノ岳、鍋割山、大山 |
| `surroundingCandidate` | 11 | 富士山、大菩薩嶺、雲取山、三ツ峠山、三頭山、越前岳、神山、万三郎岳、箱根駒ヶ岳、大岳山、金時山 |

現在の `regions` には、丹沢に加えて富士山周辺、箱根、奥多摩、大菩薩、天城、愛鷹の地域ラベルもある。これは上記の周辺候補を分類するためで、複数地域の正式対応を意味しない。

### 2.2 地形の粒度と容量

| 地形粒度 | タイル数 | 圧縮後容量 | 用途 |
| --- | ---: | ---: | --- |
| 約4m | 1,122 | 40.7MiB | 丹沢中心部の詳細な見通し判定 |
| 約8m | 289 | 13.3MiB | 詳細域の欠損補完と中間粒度 |
| 約62〜63m | 42 | 2.7MiB | 富士山・箱根・奥多摩等を含む周辺の粗い見通し確認 |

このため、17座だから60MBなのではない。4m前後の標高格子を広い面積で持っているためであり、全容量の約99%が地形である。

## 3. パック全体のデータの流れ

```text
人が確認したJSON             国土地理院の標高PNG
Data/Bootstrap/               Data/Generated/GSI/（Git管理外）
        │                                │
        ├─ 山・施設・出典の検証          ├─ 取得計画、原本SHA-256
        │                                │
        └─────────── パック生成ツール ───┘
                              │
               catalog.sqlite + terrain.lzfse
                              │
                 manifest.json + manifest.sig
                              │
                   R2の静的HTTPS配信
                              │
                  iPhoneで署名・整合性検証
                              │
               Application Support/OfflinePackages
```

生成元の主な設定は次のとおりである。

| 役割 | 場所 |
| --- | --- |
| 山・施設の正本JSON | `Data/Bootstrap/tanzawa-bootstrap-v1.json` |
| 地形取得プロファイル | `Data/OfflinePackages/tanzawa-dem-acquisition-v1.json` |
| 詳細パックの設定 | `Data/OfflinePackages/tanzawa-detailed-v1.json` |
| 出典・取得記録 | `Data/SourceManifests/*.yaml` |
| 生成・署名ツール | `Tools/OfflinePackageBuilder/` |

## 4. ファイル形式

### 4.1 `manifest.json`

パックを導入する前に読む小さな管理ファイルである。次の情報を持つ。

| 項目 | 意味 |
| --- | --- |
| `formatVersion` | manifest形式の版 |
| `packageID` | パックの固定ID。丹沢は `jp.kanagawa.tanzawa` |
| `contentVersion` | データ内容の版。内容が変わった時に上げる |
| `schemaVersion` | SQLite／地形形式の読込互換性の版 |
| `bounds` | パック全体の地理範囲 |
| `files` | `catalog.sqlite` と `terrain.lzfse` のパス、バイト数、SHA-256 |
| `keyID` / `signatureAlgorithm` | 署名を検証する公開鍵の識別子と方式 |
| `sourceManifestIDs` | 出典・取得記録への参照 |

`manifest.sig` は `manifest.json` の生バイト列をEd25519で署名した64byteのファイルである。署名、ファイルサイズ、SHA-256、SQLite、地形タイルの順に検証し、どれかが失敗したパックは導入しない。

### 4.2 `catalog.sqlite`

SQLiteの読み取り専用データベースである。アプリは外部入力として扱い、`integrity_check`、外部キー、schema、値域を確認してから読む。

#### 論理的な関連

```text
regions 1 ── * mountains 1 ── * mountain_names
                   │
                   └── * mountain_points_of_interest * ── 1 points_of_interest
                                                              │
                 trailhead_access_points / search_areas ─────┘

source_links 1 ── * entity_sources * ── 山頂・施設・地形タイル

terrain_tiles ──→ terrain.lzfse の offset / 圧縮サイズ / SHA-256
```

#### テーブル一覧

| テーブル | 保存単位 | 主な情報 | 現行詳細パック 1.0.1 |
| --- | --- | --- | --- |
| `package_metadata` | パック | schema版、内容版、パックID、Source Manifest ID | あり |
| `regions` | 山域ラベル | ID、表示名、都道府県名 | 7件 |
| `mountains` | 山頂 | 正式名、検索名、中心／周辺候補、緯度経度、標高、更新日 | 17件 |
| `mountain_names` | 山頂の名称 | 正式名・別名、検索用正規化名 | 42件 |
| `points_of_interest` | 施設 | 種別、名称、任意座標、概要、公式URL、確認日 | テーブルあり、0件 |
| `mountain_points_of_interest` | 山頂と施設の関係 | 山ごとの表示順を含む関連 | テーブルあり、0件 |
| `source_links` | 出典 | 提供者、URL、ライセンス、確認日、帰属表示、加工メモ | 1件 |
| `entity_sources` | データと出典の関係 | entity種別、entity ID、source ID | 地形タイルに使用 |
| `terrain_tiles` | 地形タイルの索引 | 範囲、解像度、256×256、ファイル位置・サイズ・ハッシュ | 1,453件 |

現在の同梱詳細パックは、古いschema v1互換形式である。このため `mountains.yamap_url`、`point_of_interest_details`、`trailhead_access_points`、`trailhead_search_areas`、および施設関連の `display_order` 列はまだ含まない。

一方、現在の生成ツールと正本JSONは次の拡張を生成できる状態にある。次の**実データ更新版**で収録する対象であり、現在の60MBパックに既に入っているという意味ではない。

| 拡張テーブル・列 | 保存するもの | 必要な理由 |
| --- | --- | --- |
| `mountains.yamap_url` | 人が照合したYAMAP山ページURL | 山詳細からの一方向リンク |
| `point_of_interest_details` | 営業期間、予約、料金、収容人数、営業時間等の確認済み属性 | 未確認値を空や推測で埋めないため |
| `mountain_points_of_interest.display_order` | 山詳細での施設表示順 | 同じ施設種別の順番を固定するため |
| `trailhead_access_points` | 登山口 → 駐車場・バス停・ロープウェイ・代表温泉 | アクセス先を登山口単位で示すため |
| `trailhead_search_areas` | 登山口・最寄駅周辺の外部地図検索地点 | コンビニ・食事等を網羅収録しないため |

`Data/Bootstrap/tanzawa-bootstrap-v1.json` には施設・アクセス関係の正本データがあり、現行パックへ反映していないことが、オフラインパック完成に向けた主なデータ差分である。

### 4.3 `terrain.lzfse`

地形本体は、WebメルカトルXYZタイルごとの256行×256列の標高格子である。

| 項目 | 形式 |
| --- | --- |
| ファイル先頭 | 16byteヘッダー（`YLTF`、形式版、ヘッダー長、タイル数、flags） |
| 1セル | 1m単位の符号付きInt16標高値 |
| 欠損セル | `-32768` |
| 1タイルの生データ | 256 × 256 × 2byte = 131,072byte（128KiB） |
| 圧縮 | タイルごとのLZFSE圧縮 |
| 読込位置 | `terrain_tiles.offset_bytes` と `compressed_bytes` |
| 改ざん・破損確認 | 圧縮解除後のSHA-256を `terrain_tiles.sha256` と照合 |

アプリは現在地を含むタイルを索引から探し、重なる場合は解像度が細かいものを優先する。したがって、詳細域と周辺粗地形を同じパックに混在させられる。

## 5. データの単位と更新単位

| 対象 | 保存単位 | 更新単位 | 備考 |
| --- | --- | --- | --- |
| 山頂 | 1座 | 山域パックの内容版 | 山名・標高・座標・別名 |
| 施設 | 1施設 | 山域パックの内容版 | 施設だけの独立配布は未実装 |
| 山頂と施設の関係 | 1関連 | 山域パックの内容版 | 例: 塔ノ岳 → 登山口 |
| 地形 | 256×256セルの1タイル | 山域パックの内容版 | 山頂数とは独立した容量要因 |
| 出典 | 1情報源 | 山域パックの内容版 | 画面表示とSource Manifestへ追跡 |
| 天気 | 山頂・取得時刻 | パック外キャッシュ | WeatherKit。オフラインパックに固定保存しない |
| メモ・お気に入り・写真 | 利用者の記録 | パック外の端末保存 | パック削除・更新で失わない |

MVPでは施設の変更も `catalog.sqlite` を含む山域パック全体の更新として配る。地形を再ダウンロードさせる負担が実測で問題になった場合だけ、将来の形式改定として施設情報を別配布物へ分ける。

## 6. 地形プロファイル比較との関係

地形の細かさは通常版のアプリ利用者が選ぶ設定ではなく、パック生成時のプロファイルで決める。比較期間中だけ、Debugビルドには現地検証用の選択画面を出す。選択値はこのiPhone内に保存され、再起動後に選択したパックを見通し判定へ使う。通常版では、この操作も選択値も利用しない。

| プロファイル | 中心詳細域 | 周辺域 | 目的 |
| --- | --- | --- | --- |
| `detailed` | 約4m中心 | 約62m | 現行60MB版。比較の基準 |
| `standard` | 約8m中心 | 約62m | 容量と見通し判定の中間案 |
| `compact` | 約16m中心 | 約124m | 容量優先案 |

比較時は、山頂・出典を同じにし、`terrain.lzfse` と `terrain_tiles` のみを主に変える。容量、パック導入時間、カメラ開始後の読込、固定リプレイ、現地の見通し判定を同じ条件で比較する。現行の詳細版だけは古い生成物のため施設0件であり、標準・軽量版には現在の正本から施設20件が入る。この差はARの地形比較に影響しないが、正式採用前には3プロファイルを同じ施設カタログで再生成して揃える。結果をSource Manifestへ残し、正式配布には採用した1種類だけを使う。

## 7. 現時点の未収録・未対応事項

- 現行の詳細パックには山小屋、登山口、駐車場、交通、温泉などの施設レコードがまだ入っていない。
- 登山道の線、ルート、地図画像、GPSトラック、活動記録は保存しない。
- 現在・予報・警報・交通のリアルタイム値は保存しない。
- 全国16,000座の詳細地形を1パックへ入れる設計ではない。全国規模で扱う場合は軽量な山頂索引と山域ごとの地形パックを分ける。

次の実データ更新では、施設データを実際の `catalog.sqlite` へ反映し、同時に地形プロファイル比較の結果を踏まえて正式な地形粒度を決める。

## 8. 検証と改定ルール

パック生成時に、入力SHA-256、SQLite整合性、外部キー、地形の範囲・offset・サイズ・SHA-256、LZFSE圧縮往復、Ed25519署名を検証する。端末導入時も同等の安全確認を行い、失敗時は直前の正常パックを保持する。

テーブル・列・地形形式を変更して既存アプリと互換でなくなる場合は、`schemaVersion` を上げる。山・施設・地形の実データだけを変更する場合は、`contentVersion` を上げる。新しい版を公開する前に、Source Manifest、内容版、出典表示、実機導入・機内モード確認を対応付ける。
