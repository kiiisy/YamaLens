# YamaLens オフラインパック設計方針

> 本書はオフラインパックの補助設計資料である。MVPの範囲、パック形式、初期値、
> セキュリティ要件は `YamaLens_事前決定事項.md` と基本設計書を正とし、矛盾時は
> 正本を優先して本書を更新する。

> パック内のファイル形式、SQLiteのテーブル、収録単位、現行丹沢パックの実データは
> [YamaLens_オフラインパックデータ設計書.md](YamaLens_オフラインパックデータ設計書.md) を参照する。

## 1. 目的

YamaLensは、通信が不安定または利用できない山中でも、カメラARによる山の候補表示、山の検索、基本的な山・施設情報の確認を可能にする。

オフラインパックは、全国の情報を端末へ一括保存するためのものではない。ユーザーがよく訪れる地域に必要なデータだけを、端末へ選択的に保存する仕組みである。

## 2. 基本方針

- オフラインでの山特定はMust要件とする。
- 最初の対象地域は丹沢山地とする。
- 天気など鮮度が重要な情報はパックへ含めず、通信可能時に取得・キャッシュする。
- 将来の複数ユーザー対応では、気象はオフラインパックと別の共有キャッシュとして配信する。全国の山を一括定時取得せず、閲覧された山を中心に取得し、正式対応山域だけを必要に応じて先行更新する。
- お気に入り、登頂済み、山ノートなどの個人データはパックと分離して端末に保存する。パックを削除しても失われない。
- ユーザーには分かりやすい山域名で見せるが、内部のデータ管理は固定サイズの地形タイルを基本とする。
- パックのダウンロードはユーザー主導を基本とし、自動取得は設定で明示的に許可した場合のみ行う。

## 3. オフラインで使える機能と使えない機能

| 区分 | 内容 |
|---|---|
| オフラインで使える | 現在地・端末の方位／姿勢と地形・山頂データを用いたAR候補表示、山名検索、標高・座標・基本説明、保存済みの登山口・山小屋の基本情報、個人データ |
| 通信時に更新する | 天気、警報・雷情報。施設の変動情報は承認済み情報源からパック作成工程で低頻度に取得し、検証済みパック更新として配布する |
| オフラインで保証しない | 最新性が必要な安全情報、リアルタイム交通・営業情報、最新の気象判断 |

AR表示はクラウド画像認識に依存しない。GPS、真方位、端末姿勢、カメラ視野角、山頂座標、DEM（標高モデル）・稜線データを組み合わせて、視界内にあり得る山頂を候補として表示する。

## 4. パックに含めるデータ

### 4.1 Base Pack（大きく、更新頻度が低い）

- DEM・地形タイル
- 稜線・AR表示用の補助データ
- 山頂の名称、標高、座標、別名
- 検索用インデックス
- 基本的な登山口・山小屋・施設の位置情報

### 4.2 Info Overlay（小さく、更新頻度が比較的高い）

- 山小屋の営業期間、予約要否、連絡先、公式リンク、最終確認日
- 登山口、駐車場、公共交通、ロープウェイ、温泉の案内と公式リンク
- 山の説明文、注意書き、データ更新日時

Base PackとInfo Overlayを分けることで、山小屋や公式リンクだけが変わった場合に、大きな地形データを再ダウンロードさせずに済む。

MVPの配布形式では、情報の分類としてBase PackとInfo Overlayを用いるが、配布物は
正本で定める `catalog.sqlite` と `terrain.lzfse` の2ファイルとする。Info Overlayを
独立した配布物に分けるのは、manifestの形式・署名・検証・ロールバックを拡張する
正本改定後の将来対応とする。

### 4.2.1 開発用ARテストパック

天候と移動機会に合わせて現地検証先を変更できるよう、開発ビルド専用のARテストパックを山域単位で作成できる。

- 山頂、周辺候補、DEM、出典、診断に必要な最小メタデータを含める。
- 山小屋、登山口、交通、駐車場、温泉、気象、アクセスの網羅性は要件としない。
- 高尾・陣馬に加え、直近の訪問予定に対応する八ヶ岳、仙丈ヶ岳・南アルプス北部、男体山・日光連山、谷川岳・谷川連峰を対象とする。各パックには現地の主要峰と、候補半径内で識別価値が高い周辺主峰を収録する。
- Debugビルドで「ARテスト用・詳細情報なし」と表示し、正式対応パック、ホームの対応地域、利用者向け自動ダウンロード候補へ混在させない。
- 正式パックと同じ署名、ハッシュ、SQLite、地形境界の検証経路を通し、パック形式そのものを別方式にしない。
- Debugの通常起動では、丹沢を含む6山域の開発用パックを一式として保存・削除する。カメラ候補は各カタログをIDで重複排除して統合し、ホーム、検索、マイの正式データは丹沢のまま維持する。
- 見通し判定と予測稜線に使うDEMは、現在地を含む各パックの詳細地形範囲から中心が最も近い1パックを自動選択する。範囲外では別パックのDEMを推測適用せず「地形未確認」とする。カメラ画面には選択中の山域を表示する。
- Xcodeの山域別起動引数は、自動選択を無効にして1パックだけを再現する診断用途として維持する。

### 4.3 パックに含めないデータ

- 現在・予報の天気
- 気温、風速・風向、降水、雲量、降雪、雷などの最新気象データ
- 個人メモ、お気に入り、登頂済み状態
- 地図・ルート・活動記録（YAMAP等の役割であり、YamaLensの対象外）

## 5. パックの単位と境界

### 5.1 ユーザーに見せる単位：山域

パックは「山ごと」ではなく、登山者が理解しやすい山域単位で提示する。

例：

- 丹沢山地
- 奥多摩
- 秩父・奥秩父
- 高尾・陣馬
- 八ヶ岳
- 仙丈ヶ岳・南アルプス北部
- 男体山・日光連山
- 谷川岳・谷川連峰
- 箱根
- 富士山周辺

ただし、これらは永久に固定された地理的・行政的区分ではない。パック名と範囲は、利用状況、データ量、アクセス圏、現地でのAR精度を踏まえて見直せるものとする。

### 5.2 内部の単位：機械的な地形タイル

山域境界を人手だけで厳密に決めると、主観的になり、運用負荷も高くなる。そのため、実データは全国を一定ルールで区切った地形タイルとして管理する。

```text
画面上の「丹沢山地パック」
  = 丹沢を覆う地形タイル群
  + 山頂・施設・検索データ
  + 情報更新用Overlay
```

山域パックは、複数タイルの集合として定義する。将来、境界を広げたり表示名を変えたりしても、タイルや内部IDを使い回せる。

### 5.3 境界対策

パック境界の近くで、見えている山が突然候補から消えないようにする。

- 山域の外周にはAR判定用の重複領域（バッファ）を持たせる。
- 重複領域には、必要最小限の山頂データと低解像度の地形データを含める。
- パック外の候補には「周辺データ」などの状態を表示し、詳細情報が不足する場合を明示する。

## 6. ダウンロード・更新・削除の体験

### 6.1 マイページでの見せ方

マイページには、ダウンロード済みパックの概要を最大2件程度表示し、全件は「パックを管理」から確認する。

```text
オフラインパック                         パックを管理 >
ダウンロード済み 1件・使用中 286 MB

[ 丹沢山地  最新・286 MB                    > ]
```

個別のパックカードには「管理する」を置かない。個別カードをタップすると詳細画面へ、右上の「パックを管理」から一覧・追加・更新・削除へ進む。

### 6.2 ダウンロード設定

この節の自動取得・複数山域向け設定は個人利用MVP後の設計である。個人利用MVPでは、丹沢パックだけを静的HTTPS配信から手動で導入・更新・削除する。

- 自動取得を有効にした場合のWi-Fi接続時のみダウンロード：初期値ON
- モバイル通信での自動取得：初期値OFF、明示的な許可が必要
- 自動取得：初期値OFF
- 自動取得を有効にする場合は、Wi-Fi時のみ・容量上限・対象範囲を設定可能にする
- 保存容量の使用量と上限を表示する
- パックの自動削除は行わない。削除はユーザーの明示操作だけとする

### 6.3 自動取得の位置付け

これは複数山域の配布を開始した後の拡張であり、個人利用MVPでは実装しない。

GPSで近くの地域を検出してダウンロード候補を出すことはできるが、無制限の自動ダウンロードは行わない。

```text
近くに未保存の対象地域がある
  → 画面内で候補表示
  → Wi-Fi接続・自動取得ON・容量条件を満たす場合のみ取得
```

ユーザーが事前にパックを入れる体験を基本とし、位置情報は補助的な提案に使う。

### 6.4 更新確認と配信アクセス

- オフラインパックの更新確認と気象更新を同じ要求・同じキャッシュへまとめない。パック本体、manifest、気象スナップショットの使用量を別々に計測する。
- 複数ユーザー対応時の自動更新確認は、小さなmanifestに対して `ETag`／`If-None-Match` を使用し、同じパックについて原則24時間に1回以下とする。利用者の明示的な更新確認は別に提供できるが、変更がない場合にパック本体を再取得しない。
- パック本体は内容版が変わり、利用者が導入または更新を実行した時だけ取得する。CDNキャッシュを利用し、手動保存済みパックをアクセス数削減のために自動削除・再取得しない。
- 気象は小さなJSONとしてパックから分離する。将来の共有キャッシュでは山ID・検証済み山頂座標単位のオンデマンド取得を基本とし、全国山頂索引に存在するだけの山を定時巡回しない。

## 7. PoC版と将来版

### 7.1 開発用PoC：複数山域のAR現地検証

目的は、天候のよい訪問可能な山域を選び、オフラインでAR山候補が実用になるかを継続的に確かめることである。初期正式対応地域は丹沢のままとし、丹沢外のテストパックは正式対応を意味しない。

```text
元データを用意
  → Macで対象山域のARテストパックを生成
  → YamaLensアプリへ同梱
  → iPhone 15 Proへインストール
  → 晴天と訪問機会が得られた地域で完全オフライン検証
```

これはMVP以前の開発用試作であり、利用者向けMVPのパック操作要件を変更しない。
最初のPoCでは、丹沢の中心6座と富士山等の周辺候補11座を生成済み `bootstrap.sqlite` へ収録し、読み取り専用SQLite、schema検証、Bundle同梱、一覧・検索・AR候補の接続を確認する。続いて、訪問予定と天候に応じて丹沢外の山域を一つずつ追加する。周辺候補やテスト対象山はホームの丹沢向け紹介へ混在させない。詳細地形については、取得済みの国土地理院256×256 PNG／テキスト標高タイルから、原本SHA-256付き索引、SQLite、LZFSE地形、manifest、Ed25519署名を生成する開発用ツールを使用する。実原本の取得・利用手続確認と静的配信は、その生成基盤とは分離して進める。

生成後の現地検証では、署名済み4ファイルをGit追跡外のDebug用Resourceへ明示操作で複製する。Debugビルドはこれを一時領域へ複製し、利用者向け配信と同じ検証・アトミック切り替えを通して導入する。Releaseビルドにローカル導入経路は含めず、静的HTTPS配信の仕様も変更しない。
開発用PoCでは以下を不要とする。

- Cloudflare R2
- 常時動作するバックエンド
- ユーザーアカウント
- 静的HTTPS配信からのバックグラウンドダウンロード
- 配布先の差分更新

パックの変更は内容版を更新して再生成・再同梱し、アプリを再ビルド後にパック管理画面から明示的に導入する。

### 7.2 個人利用MVP：Cloudflare R2による静的HTTPS配信

個人利用MVPでは、丹沢パックのアプリ内ダウンロード、更新、削除を提供する。これはApp Store公開の可否とは独立した、開発者本人が継続利用・現地検証するための完成条件である。

配布元にはCloudflare R2のStandardストレージを採用し、`https://packages.yamalens.com/tanzawa/<contentVersion>/` の独自ドメインによる静的HTTPS URLで署名済みパックを公開する。`r2.dev` URLは開発確認に限定する。アプリは読取り専用の配布URLだけを使用し、R2の書込み用トークンやS3認証情報を含めない。

アプリは先に `https://packages.yamalens.com/tanzawa/release.json` と `release.sig` を取得・署名検証し、一覧が指定する内容版の4ファイルを取得する。一覧とパックmanifestは同じEd25519公開鍵で検証する。新しい版がない場合、更新確認は再ダウンロードを行わない。

丹沢の初期容量目標は150〜400MBであり、R2 Standardの月間無料枠（ストレージ10GB、Class A操作100万件、Class B操作1,000万件）の範囲で個人利用を始められる見込みである。ただし無料枠は費用上限ではないため、R2の請求設定・使用量アラートを有効にし、公開前にデータ利用条件と再配布可否を確認する。

```text
Mac上のパック作成ツール
  → パック本体と manifest.json を生成
  → R2の内容版フォルダへ4ファイルをアップロード
  → 署名済み配布一覧を最後にR2へアップロード
  → アプリが配布一覧とmanifest.jsonを取得・検証
  → ユーザーが必要な地域だけダウンロード
```

静的配信元の役割は完成したファイルの保管・配布であり、山データの収集・更新・パック化は行わない。

### 7.3 将来版：必要に応じたAPI追加

アプリ向けAPIは、次の要件が出たときに追加する。

- アプリのバージョンに応じて配布パックを変える
- ダウンロード条件や利用制限を設ける
- 期限付きURLを発行する
- 課金済み地域パックの配布判定をする
- 更新情報をアプリ向けに加工して返す
- 複数ユーザーでWeatherKit呼出しを共有し、同じ山の同時・反復取得を抑える

アカウント、複数端末同期、クラウド上の山ノート保存が必要になった場合は、静的配信とは分離したBaaSを改めて検討する。

気象共有キャッシュを追加する場合も、汎用的な山APIやユーザーアカウントを同時に導入しない。閲覧要求を受けた山だけを取得し、先行更新は正式配布中の山域へ限定する。WeatherKit秘密鍵をサーバー側Secretだけで扱い、検証済み気象JSONはパックとは別の保存期間・ロールバック方針で配信する。

## 8. パック作成・配布の運用

### 8.1 担当範囲

| 作業 | 担当 |
|---|---|
| 元データの選定、内容確認、利用条件の確認 | YamaLens運営者（初期は開発者本人） |
| 元データの整形・検証・パック化 | Mac上のパック作成ツール |
| パックと更新情報の保管・配布 | Cloudflare R2（Standardストレージ、独自ドメインの静的HTTPS配信） |
| パックの取得、更新、削除、端末保存 | YamaLensアプリ |

### 8.2 パック作成ツール

パック作成ツールは、開発用Macで必要なときだけ実行する。常時動作するサーバーではない。

処理例：

```text
元データ取込
  → 座標・名称・施設情報の検証
  → 地形タイル・検索DB・Overlayの生成
  → 圧縮・チェックサム作成
  → manifest.json更新
  → Cloudflare R2へアップロード
```

初期はPythonを第一候補とする。地形データ、CSV・JSON、SQLite、圧縮ファイル、検証処理を扱いやすいためである。

丹沢の地形粒度はアプリ利用者が切り替える設定にはせず、パック作成時に `detailed`、`standard`、`compact` のいずれかを選ぶ。選択値は取得計画へ記録し、各プロファイルの原本・索引・生成先を分離する。容量だけで公開版を切り替えず、読み込み時間と固定リプレイ／現地での見通し判定も比較し、採用したプロファイルをSource Manifestと内容版へ記録する。

Debugビルドでは、生成済みの丹沢 `detailed`、`standard`、`compact` パックを別bundleとして同梱できる。Xcodeの起動引数 `-tanzawa-terrain-profile <profile>` で一つを固定選択し、カメラ画面とパック管理画面へ選択プロファイルを明示する。利用者向けRelease版やR2の配布一覧にはこの切替を含めない。比較後に採用した一種類だけを正式パックとして配布する。

施設情報は、利用条件、robots.txt、再利用条件、取得頻度、抽出項目をSource Manifestへ記録した承認済みの公式情報源だけを対象に自動取得できる。API、RSS、GTFS等を優先し、HTMLは情報源専用の抽出規則で処理する。アプリは取得処理を行わず、取得結果は差分・形式・上限を検証してからInfo Overlay相当のデータへ反映する。新規情報源、抽出規則の変更、大幅な差分、曖昧な営業・通行情報だけを人が確認する。

初期の自動取得は、取得候補を正本JSONへ直接書き込まず、原文スナップショット、取得メタデータ、抽出候補、現行値との差分を生成するところまでとする。人が差分を承認した後にだけ既存のSQLite・署名済みパック生成へ進める。MVPでは低頻度更新のため既存の山域パックを内容版更新し、Info Overlayの独立配布は、施設だけの更新で地形ファイル再取得の負担が問題になった場合に実測結果をもとに判断する。

### 8.3 更新頻度

| データ | 更新の考え方 |
|---|---|
| 地形・山頂座標 | ほぼ更新不要。必要時のみBase Packを更新 |
| 山小屋・登山口・公式リンク | シーズン前、承認済み情報源の低頻度な定期取得時、または変更確認時にInfo Overlayを更新。情報源の更新頻度と利用条件を優先する |
| 天気 | パック化しない。通信時取得・キャッシュ |

毎週すべての地域パックを作り直す運用にはしない。変更が必要な情報だけを小さく更新する。

### 8.4 個人利用MVPの更新手順

Cloudflare Workersは、この手順では使用しない。データ収集、整形、パック生成、署名は開発用Mac上の既存Pythonツールで行い、R2は完成済みファイルを配布するだけにする。

1. 承認済み情報源の変更を確認し、内容が実際に変わる場合だけ `contentVersion` を上げる。テストのためだけに公開版を更新しない。
2. `build_detailed_pack.py build` で新しい内容版の4ファイルを生成する。Ed25519秘密鍵はリポジトリ外で管理し、アプリ・R2・Gitへ置かない。
3. `build_release_index.py` で同じ秘密鍵を用い、同じ内容版を示す `release.json` と `release.sig` を生成する。
4. R2の `tanzawa/<contentVersion>/` へ、`manifest.json`、`manifest.sig`、`catalog.sqlite`、`terrain.lzfse` の順序を問わず4ファイルすべてアップロードする。既存の内容版フォルダは削除しない。
5. 4ファイルの公開HTTPS URLとサイズを確認した後、R2の `tanzawa/` 直下に `release.json`、`release.sig` の順でアップロードして配布一覧を切り替える。配布一覧を先に切り替えない。
6. 実機で「更新を確認」を実行し、新しい内容版、ダウンロード、署名・整合性検証、機内モードでの利用を確認する。更新に失敗しても直前の正常なパックを保持する。

現在公開中の `1.0.2` は更新機能確認用に作成した同一データのテスト版である。次の実データ更新時は、その変更内容に基づく新しい内容版を生成する。

## 9. データ品質・ライセンス

- 元データごとに出典、利用許諾・ライセンス、取得日、更新日を管理する。
- YAMAP・ヤマレコ等の画像やデータを無断で取得・転載しない。
- 写真は、ユーザー自身の写真、適法なライセンスの写真、または正確な地形カードを使用する。
- 山小屋営業・交通・登山道状況は誤りが安全に関わるため、最終確認日と公式情報へのリンクを必ず表示する。
- AR候補は確定的な同定結果として断言せず、低精度・データ不足・センサー異常時にはその状態を表示する。

## 10. 初期の決定事項

1. 開発用PoCでは丹沢および選択した丹沢外のARテストパックをアプリへ明示的に同梱し、天候と訪問機会に合わせて完全オフライン検証を行う。丹沢外パックは開発ビルド専用で、利用者向けMVPの正式対応地域やパック操作を置き換えない。
2. 個人利用MVPでは、Cloudflare R2の独自ドメインによる署名済み静的HTTPS配信元から、丹沢パックを取得・更新・削除する。App Store公開や第三者向け運用は別の完了条件とする。
3. パック作成ツールはMac上で必要時に動かす。初期実装言語はPythonを第一候補とする。
4. ユーザー向けのパックは山域単位、内部の地形データはタイル単位で管理する。
5. 自動ダウンロード、Wi-Fiのみ、モバイル通信の選択はMVP後に追加する。追加時は自動ダウンロードを初期値OFF、Wi-Fiのみを初期値ONとする。
6. パックを削除しても個人の山ノート・お気に入り・登頂済み状態は削除しない。
7. 天気・リアルタイム情報はオフラインパックへ含めない。
