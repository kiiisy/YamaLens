# YamaLens オフラインパック設計方針

> 本書はオフラインパックの補助設計資料である。MVPの範囲、パック形式、初期値、
> セキュリティ要件は `YamaLens_事前決定事項.md` と基本設計書を正とし、矛盾時は
> 正本を優先して本書を更新する。

## 1. 目的

YamaLensは、通信が不安定または利用できない山中でも、カメラARによる山の候補表示、山の検索、基本的な山・施設情報の確認を可能にする。

オフラインパックは、全国の情報を端末へ一括保存するためのものではない。ユーザーがよく訪れる地域に必要なデータだけを、端末へ選択的に保存する仕組みである。

## 2. 基本方針

- オフラインでの山特定はMust要件とする。
- 最初の対象地域は丹沢山地とする。
- 天気など鮮度が重要な情報はパックへ含めず、通信可能時に取得・キャッシュする。
- お気に入り、登頂済み、山ノートなどの個人データはパックと分離して端末に保存する。パックを削除しても失われない。
- ユーザーには分かりやすい山域名で見せるが、内部のデータ管理は固定サイズの地形タイルを基本とする。
- パックのダウンロードはユーザー主導を基本とし、自動取得は設定で明示的に許可した場合のみ行う。

## 3. オフラインで使える機能と使えない機能

| 区分 | 内容 |
|---|---|
| オフラインで使える | 現在地・端末の方位／姿勢と地形・山頂データを用いたAR候補表示、山名検索、標高・座標・基本説明、保存済みの登山口・山小屋の基本情報、個人データ |
| 通信時に更新する | 天気、警報・雷情報、山小屋の営業状況、交通・ロープウェイ運行、駐車場混雑、公式サイトの最新情報 |
| オフラインで保証しない | 最新性が必要な安全情報、リアルタイム交通・営業情報、最新の気象判断 |

AR表示はクラウド画像認識に依存しない。GPS、真方位、端末姿勢、カメラ視野角、山頂座標、DEM（標高モデル）・稜線データを組み合わせて、視界内にあり得る山頂を候補として表示する。

## 4. パックに含めるデータ

### 4.1 Base Pack（大きく、更新頻度が低い）

- DEM・地形タイル
- 稜線・AR表示用の補助データ
- 山頂の名称、標高、座標、別名
- 検索用インデックス
- 基本的な登山口・山小屋・施設の位置情報

### 4.2 Info Overlay（小さく、更新頻度が比較的高い）

- 山小屋の営業期間、予約要否、連絡先、公式リンク、最終確認日
- 登山口、駐車場、公共交通、ロープウェイ、温泉の案内と公式リンク
- 山の説明文、注意書き、データ更新日時

Base PackとInfo Overlayを分けることで、山小屋や公式リンクだけが変わった場合に、大きな地形データを再ダウンロードさせずに済む。

MVPの配布形式では、情報の分類としてBase PackとInfo Overlayを用いるが、配布物は
正本で定める `catalog.sqlite` と `terrain.lzfse` の2ファイルとする。Info Overlayを
独立した配布物に分けるのは、manifestの形式・署名・検証・ロールバックを拡張する
正本改定後の将来対応とする。

### 4.3 パックに含めないデータ

- 現在・予報の天気
- 気温、風速・風向、降水、雲量、降雪、雷などの最新気象データ
- 個人メモ、お気に入り、登頂済み状態
- 地図・ルート・活動記録（YAMAP等の役割であり、YamaLensの対象外）

## 5. パックの単位と境界

### 5.1 ユーザーに見せる単位：山域

パックは「山ごと」ではなく、登山者が理解しやすい山域単位で提示する。

例：

- 丹沢山地
- 奥多摩
- 秩父・奥秩父
- 高尾・陣馬
- 箱根
- 富士山周辺

ただし、これらは永久に固定された地理的・行政的区分ではない。パック名と範囲は、利用状況、データ量、アクセス圏、現地でのAR精度を踏まえて見直せるものとする。

### 5.2 内部の単位：機械的な地形タイル

山域境界を人手だけで厳密に決めると、主観的になり、運用負荷も高くなる。そのため、実データは全国を一定ルールで区切った地形タイルとして管理する。

```text
画面上の「丹沢山地パック」
  = 丹沢を覆う地形タイル群
  + 山頂・施設・検索データ
  + 情報更新用Overlay
```

山域パックは、複数タイルの集合として定義する。将来、境界を広げたり表示名を変えたりしても、タイルや内部IDを使い回せる。

### 5.3 境界対策

パック境界の近くで、見えている山が突然候補から消えないようにする。

- 山域の外周にはAR判定用の重複領域（バッファ）を持たせる。
- 重複領域には、必要最小限の山頂データと低解像度の地形データを含める。
- パック外の候補には「周辺データ」などの状態を表示し、詳細情報が不足する場合を明示する。

## 6. ダウンロード・更新・削除の体験

### 6.1 マイページでの見せ方

マイページには、ダウンロード済みパックの概要を最大2件程度表示し、全件は「パックを管理」から確認する。

```text
オフラインパック                         パックを管理 >
ダウンロード済み 1件・使用中 286 MB

[ 丹沢山地  最新・286 MB                    > ]
```

個別のパックカードには「管理する」を置かない。個別カードをタップすると詳細画面へ、右上の「パックを管理」から一覧・追加・更新・削除へ進む。

### 6.2 ダウンロード設定

- 自動取得を有効にした場合のWi-Fi接続時のみダウンロード：初期値ON
- モバイル通信での自動取得：初期値OFF、明示的な許可が必要
- 自動取得：初期値OFF
- 自動取得を有効にする場合は、Wi-Fi時のみ・容量上限・対象範囲を設定可能にする
- 保存容量の使用量と上限を表示する
- パックの自動削除は行わない。削除はユーザーの明示操作だけとする

### 6.3 自動取得の位置付け

GPSで近くの地域を検出してダウンロード候補を出すことはできるが、無制限の自動ダウンロードは行わない。

```text
近くに未保存の対象地域がある
  → 画面内で候補表示
  → Wi-Fi接続・自動取得ON・容量条件を満たす場合のみ取得
```

ユーザーが事前にパックを入れる体験を基本とし、位置情報は補助的な提案に使う。

## 7. PoC版と将来版

### 7.1 開発用PoC：丹沢の現地検証

目的は、オフラインでAR山判定が実用になるかを確かめることである。

```text
元データを用意
  → Macで丹沢パックを生成
  → YamaLensアプリへ同梱
  → iPhone 15 Proへインストール
  → 現地で完全オフライン検証
```

これはMVP以前の開発用試作であり、利用者向けMVPのパック操作要件を変更しない。
最初のPoCでは、丹沢の中心6座と富士山等の周辺候補11座を生成済み `bootstrap.sqlite` へ収録し、読み取り専用SQLite、schema検証、Bundle同梱、一覧・検索・AR候補の接続を確認する。周辺候補は丹沢外周の識別用で、ホームの丹沢向け紹介には混在させない。詳細地形を含むパックと署名付き静的配信は、その基盤を利用する次の実装単位とする。
開発用PoCでは以下を不要とする。

- Cloudflare R2
- 常時動作するバックエンド
- ユーザーアカウント
- パックのアプリ内ダウンロード・削除・差分更新

パックの変更は、アプリを再ビルドして端末へ入れ直すことで反映する。

### 7.2 MVP：静的HTTPS配信による配布

利用者向けMVPでは、丹沢パックのアプリ内ダウンロード、更新、削除を提供する。
配布元は署名済みの静的HTTPS配信とし、Cloudflare R2はその候補の一つに留める。
採用は配布運用・費用・アクセス制御を別途判断してから行う。

```text
Mac上のパック作成ツール
  → パック本体と manifest.json を生成
  → 静的HTTPS配信元へアップロード
  → アプリがmanifest.jsonを確認
  → ユーザーが必要な地域だけダウンロード
```

静的配信元の役割は完成したファイルの保管・配布であり、山データの収集・更新・パック化は行わない。

### 7.3 将来版：必要に応じたAPI追加

アプリ向けAPIは、次の要件が出たときに追加する。

- アプリのバージョンに応じて配布パックを変える
- ダウンロード条件や利用制限を設ける
- 期限付きURLを発行する
- 課金済み地域パックの配布判定をする
- 更新情報をアプリ向けに加工して返す

アカウント、複数端末同期、クラウド上の山ノート保存が必要になった場合は、静的配信とは分離したBaaSを改めて検討する。

## 8. パック作成・配布の運用

### 8.1 担当範囲

| 作業 | 担当 |
|---|---|
| 元データの選定、内容確認、利用条件の確認 | YamaLens運営者（初期は開発者本人） |
| 元データの整形・検証・パック化 | Mac上のパック作成ツール |
| パックと更新情報の保管・配布 | 署名済み静的HTTPS配信元（具体的な事業者は別途決定） |
| パックの取得、更新、削除、端末保存 | YamaLensアプリ |

### 8.2 パック作成ツール

パック作成ツールは、開発用Macで必要なときだけ実行する。常時動作するサーバーではない。

処理例：

```text
元データ取込
  → 座標・名称・施設情報の検証
  → 地形タイル・検索DB・Overlayの生成
  → 圧縮・チェックサム作成
  → manifest.json更新
  → 静的HTTPS配信元へアップロード
```

初期はPythonを第一候補とする。地形データ、CSV・JSON、SQLite、圧縮ファイル、検証処理を扱いやすいためである。

### 8.3 更新頻度

| データ | 更新の考え方 |
|---|---|
| 地形・山頂座標 | ほぼ更新不要。必要時のみBase Packを更新 |
| 山小屋・登山口・公式リンク | シーズン前、または変更確認時にInfo Overlayを更新 |
| 天気 | パック化しない。通信時取得・キャッシュ |

毎週すべての地域パックを作り直す運用にはしない。変更が必要な情報だけを小さく更新する。

## 9. データ品質・ライセンス

- 元データごとに出典、利用許諾・ライセンス、取得日、更新日を管理する。
- YAMAP・ヤマレコ等の画像やデータを無断で取得・転載しない。
- 写真は、ユーザー自身の写真、適法なライセンスの写真、または正確な地形カードを使用する。
- 山小屋営業・交通・登山道状況は誤りが安全に関わるため、最終確認日と公式情報へのリンクを必ず表示する。
- AR候補は確定的な同定結果として断言せず、低精度・データ不足・センサー異常時にはその状態を表示する。

## 10. 初期の決定事項

1. 開発用PoCでは丹沢山地パックをアプリに同梱し、完全オフライン検証を行う。これは利用者向けMVPのパック操作を置き換えない。
2. 利用者向けMVPでは、署名済み静的HTTPS配信元から丹沢パックを取得・更新・削除する。具体的な配布事業者は別途決定する。
3. パック作成ツールはMac上で必要時に動かす。初期実装言語はPythonを第一候補とする。
4. ユーザー向けのパックは山域単位、内部の地形データはタイル単位で管理する。
5. 自動ダウンロードは初期値OFF、Wi-Fiのみを初期値ONとする。
6. パックを削除しても個人の山ノート・お気に入り・登頂済み状態は削除しない。
7. 天気・リアルタイム情報はオフラインパックへ含めない。
