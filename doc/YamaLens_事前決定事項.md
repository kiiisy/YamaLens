# YamaLens 事前決定事項

作成日: 2026-08-17  
更新日: 2026-08-25
対象: YamaLens 初期開発（個人利用を前提としたMVP）

本書は、要求仕様書・基本設計書・UI設計書の実装前に決めておくべき判断を、現時点の開発方針として固定するための記録である。将来変更する場合は、本書を更新したうえで関連仕様も見直す。

## 1. プロダクト方針

| 項目 | 決定 |
| --- | --- |
| アプリ名 | **YamaLens** |
| 位置付け | 登山のルート・地図・活動記録アプリではなく、山の同定、登山前後の確認情報、自分の記録をまとめるiPhoneアプリ |
| 主な利用場面 | 山頂・稜線・展望地点で山を眺める時、および登山前の準備時 |
| 初期正式対応地域 | 丹沢山地。山詳細、施設、更新運用、利用者向けオフラインパックを完成させる対象とする |
| AR検証地域 | 天候と移動機会に合わせ、丹沢以外の複数山域へ開発用ARテストパックを用意できる。これは正式対応地域の追加を意味しない |
| 公開方針 | まずは個人利用。App Store公開、複数ユーザー、収益化はMVPの対象外 |
| MVPの完了 | 自分の端末で丹沢パックをHTTPSから導入・更新し、圏外で利用できること。App Store公開の可否や第三者向けの運用体制は、この完了条件に含めない |
| 対応端末 | iPhone 15 Pro／15 Pro Max以降のProモデル |
| 非対応端末 | iPad、iPhoneの通常モデル、旧OS・旧Xcodeとの互換対応 |
| 開発環境 | Xcode 26、iOS 26を前提とする |
| UIデザイン | iOS 26のLiquid Glassを標準デザイン言語として採用する。SwiftUI標準部品を優先し、ガラス表現はナビゲーションと重要な操作レイヤーへ限定する |

## 2. MVPで提供する範囲

### 実装するもの

- ホーム、山一覧、名称検索、山詳細。
- オフラインでのカメラAR候補表示。GPS・真北方位・端末姿勢・カメラ画角・保存済み山頂／地形データを使い、見えている可能性が高い山を候補として表示する。
- 山名、標高、現在地からの距離、方角、山頂付近の現在・予報・前日の気象サマリー、日の出・日の入り、山小屋、複数の登山口と登山口ごとの駐車場・公共交通・ロープウェイ・代表的な温泉、公式リンク、自分メモ・お気に入り。山詳細の既定イラストは端末内で選択した写真へ変更でき、写真は山ごとの個人データとして端末内だけに保存し、ホーム等の山カードと詳細への遷移にも反映する。登山口または最寄り駅周辺のコンビニ・食事・追加の温泉候補は、外部地図アプリの検索導線として提供する。
- ホームで、同梱の軽量丹沢データに登録した季節メタデータから「今の時期の丹沢」を紹介する。これは登山可否や安全性の推薦ではなく、詳細パック、現在地、通信、天気に依存しない固定の紹介とする。
- 位置情報を利用する「近い山」は、対応済みまたは同梱済みの基本情報を持つ山だけから表示する。候補がない場合、遠い山を近い山として代替せず、対応範囲と山名検索への導線を表示する。
- AR候補として選択した山を、利用者の明示操作で撮影し、「気になった山」として記録する。記録には写真、記録日時、任意のメモ、利用者が記録ごとに明示して有効化した場合だけ正確な視点位置を端末内へ保存する。お気に入りとは別の現地記録であり、選択した山を確実に同定した結果としては扱わない。
- よく使う出発駅を1件登録し、「現在地」または登録駅を出発地として、Apple Mapsを既定、Google Mapsを選択肢とする外部地図アプリへのアクセス案内。
- 山ごとに検証済みURLがある場合、山詳細からYAMAPのHTTPS山ページをUniversal Linkで開く一方向の外部導線。YAMAPが未導入の場合は同じページをWebで開き、計画作成はYAMAP側で行う。
- Cloudflare R2の静的HTTPS配信から行う、丹沢パックの手動導入・更新・削除。
- 開発ビルド専用の診断モードと、現地ログの再生。

### 実装しないもの

- ルート詳細、登山地図、GPSトラック、活動記録、YAMAPのアカウント・活動データ連携。山ページを開く一方向の外部導線は除く。
- AIによる回答・判断、Apple Watch、Dynamic Island、公開向けのアカウント機能・クラウド同期。
- パックの自動ダウンロード、近隣山域の自動提案、複数の正式対応地域の配布。
- 登山の可否・安全性を結論付ける機能。

## 3. 丹沢MVPのデータ範囲

| データ | 初期範囲・決定 |
| --- | --- |
| 山頂 | 丹沢山地の主要な山頂を収録する。塔ノ岳、丹沢山、蛭ヶ岳、大山、鍋割山、檜洞丸、袖平山、塔ノ岳周辺の主要ピークを優先し、富士山・箱根・奥多摩等の丹沢から識別に必要な主要山頂を「周辺候補」として含める。周辺候補は丹沢パックの境界補助であり、別山域の詳細対応を意味しない。 |
| 地形 | 丹沢周辺は詳細DEM、外側は粗いDEMを持つ多解像度構成とする。全国分の軽量な山頂索引は、後の山域追加と遠方候補表示のために持つ。 |
| 施設 | 山小屋と複数の登山口を構造化する。駐車場、主要な駅・バス停・ロープウェイ、代表的な温泉は登山口へ明示的に紐付ける。営業期間、予約、収容人数、料金等は新しい大分類へ分けず、確認済みの属性だけを各施設の詳細として持つ。コンビニ・食事・追加の温泉候補は店舗を網羅収録せず、登山口または最寄り駅周辺を外部地図で検索する地点として持つ。 |
| 施設の正確性 | 営業状況・運行状況は常に変わり得るため、アプリ内情報は補助として扱い、公式ページと更新日を必ず表示する。 |
| 登録単位 | オフラインパックは「丹沢」のような山域単位とする。現在地からの半径単位では提供しない。 |
| ARテストパック | 開発ビルド専用として、山頂、周辺候補、DEM、出典、診断に必要な最小メタデータだけを山域単位で収録できる。山詳細、施設、気象、アクセスの網羅性を保証せず、「ARテスト用・詳細情報なし」と正式対応パックから区別する。候補地域は高尾・陣馬、奥多摩、箱根・富士山周辺、実際に訪問可能なアルプスの一部等とし、天候と訪問予定に応じて選ぶ。Debugビルドでは導入済みテストパックの山頂候補を統合し、現在地を含む詳細地形範囲のDEMだけを自動選択する。 |

## 4. AR同定の品質方針

| 項目 | 決定 |
| --- | --- |
| 同定方式 | クラウド画像認識には依存しない。位置・標高・真北方位・姿勢・カメラ画角・山頂データ・地形から候補を計算する。 |
| オフライン性 | 導入済みパックの範囲内では、通信なしで候補表示・山詳細閲覧を行える。 |
| 表示の意味 | ラベルは「確定」ではなく候補。候補順位または確信度を内部で持ち、精度低下時は断定的に表示しない。 |
| 合格ライン | 開発中は複数山域のARテストパックと現地ログで候補の有用性を評価し、天候待ちの間も周辺機能の開発を並行する。初期正式対応の完了には丹沢の代表地点を少なくとも1地点含め、目視可能な主要ピークを候補一覧に安定して提示できることを必要とする。AR上のラベル位置は概略案内とし、完全な輪郭追従は目標にしない。 |
| 手動補正 | ラベルのずれを利用者が補正できるようにする。補正値は当該セッションで優先し、診断ログには保存する。 |
| ズーム | MVPでは 1x／2x／3x の段階操作。連続ズームとレンズ自動切替は実地検証後に判断する。 |
| 精度低下時 | コンパス精度・GPS精度・見通し・データ範囲の問題を表示し、検索または手動選択に切り替えられるようにする。 |

## 5. オフラインパックと通信

| 項目 | 決定 |
| --- | --- |
| 容量目標 | 初回の丹沢パックは150〜400MBを目安とし、個人利用MVPで扱うパック総量は1GB未満とする。複数地域を追加する際の利用者設定としての保存上限は、その時点で設計する。 |
| パック操作 | 利用者が導入・更新・削除を明示的に管理する。手動導入したパックをアプリが無断で削除しない。 |
| 配布元 | Cloudflare R2のStandardストレージを、YamaLens用の独自ドメインによる静的HTTPS配信元として使用する。`r2.dev` URLは開発確認に限定し、個人利用MVPでは使用しない。 |
| 自動ダウンロード | 個人利用MVPでは実装しない。後続で追加する場合は初期設定をOFFとし、有効時はWi-Fi接続時のみを既定、モバイル通信は別途明示許可とする。 |
| 未導入地域 | 個人利用MVPでは丹沢以外を配布対象にしない。近隣山域の提案は、複数山域の配布を開始するMVP後に追加する。 |
| オフラインで扱う情報 | 山頂・地形・施設の基本情報・メモ・お気に入り・日の出／日没・AR候補。 |
| オンラインで更新する情報 | 天気、施設の更新、パック更新情報。各情報には取得日時または更新日を表示する。 |

## 6. データ・外部サービスの方針

| 項目 | 決定 |
| --- | --- |
| 山頂・地形 | 国土地理院など、利用条件と出典表記を確認できる信頼性の高い公開データを利用する。配布データと画面上の出典表記を整備する。 |
| 施設情報 | 公式サイト、公開API、RSS、GTFS等を一次情報とする。名称・位置・公式URL等の基本情報は初回登録時に人が確認し、営業期間、臨時休業、運行案内等の変動情報は、承認済みの公式情報源から低頻度で自動取得できる。汎用的・無差別なスクレイピングは行わず、情報源ごとに利用条件、robots.txt、再利用条件、取得頻度、抽出項目を記録する。 |
| 補助的な地物探索 | OpenStreetMapは候補探索・補助情報としてのみ利用し、MVPの実行時依存にはしない。利用時はライセンス表示を行う。 |
| 天気 | 個人利用MVPは端末からWeatherKitを利用し、現在・予報に加えて前日の山頂付近の日別サマリーを表示する。通信できない場合は対象日が一致する端末キャッシュと取得日時を表示する。複数ユーザーへ公開する段階では、全登録山の定時巡回を行わず、閲覧された山を中心にWeatherKit REST APIの応答をサーバー側で共有キャッシュし、利用者数に比例してWeatherKit呼出しが増えない方式へ移行する。 |
| 日の出・日の入り | 端末内で計算する。 |
| アクセス案内 | 経路探索は行わず、選択した登山口・駐車場・交通施設・代表的な温泉を目的地としてApple MapsまたはGoogle Mapsへ渡す。登山口または最寄り駅周辺のコンビニ・食事・追加の温泉候補は、外部地図アプリの検索として開く。 |
| 登山サービス | 山ごとに人が対応関係を確認した `https://yamap.com/mountains/<ID>` だけをパックへ収録し、Universal Linkとして開く。YAMAP内のルート、計画、活動記録、アカウント情報は取得・保存しない。ヤマレコは条件検索がプレミアムプランへ依存し、MVPで安定した山・計画導線を提供できないため対象外とする。非公開URL schemeは使用しない。 |
| AI | MVP対象外。将来は取得済みの構造化情報を短く要約する用途だけに限定し、登山判断は行わせない。 |

## 7. 個人データ・プライバシー

| 項目 | 決定 |
| --- | --- |
| アカウント | 作らない。ログインやサーバー側の個人プロフィールは持たない。 |
| 保存場所 | メモ、お気に入り、気になった山の記録と写真、よく使う出発駅、設定、パック情報、明示保存した診断ログは端末内に保存する。 |
| 位置情報 | AR・距離・周辺提案のため、利用中に取得する。位置履歴として常時保存しない。「気になった山」の正確な視点位置は、記録ごとに利用者が明示して有効化した場合だけ保存する。 |
| カメラ | AR表示と、利用者が明示した「気になった山」の撮影に利用する。映像を常時保存・送信しない。 |
| 診断情報 | 利用者または開発者が明示操作で保存したものだけを保持する。共有前に内容を確認できるようにする。 |
| 分析・クラッシュ解析 | MVPでは外部SDKを導入しない。クラッシュ再現は開発時の診断ログで行う。 |

## 8. 更新と保守の運用

- 山頂・地形データは、データソースの更新を確認した時にパックとして更新する。
- 施設・山小屋・交通情報は、登山シーズン前、承認済み情報源の定期取得時、更新情報を把握した時に見直す。通常は低頻度の定期バッチとし、情報源の更新頻度・利用条件に合わせる。
- 自動取得はアプリ実行中に各サイトへ直接行わず、パック作成工程で実施する。取得結果は検証後に署名済みパックへ反映し、新規情報源、抽出規則の変更、取得値の大幅な変化、曖昧な営業・通行情報だけを人が確認する。
- 自動取得や解析に失敗した場合は直前の正常な値を消去・推測で置換せず、最終確認日、更新失敗または古い状態、公式リンクを表示する。
- 天気は取得日時を最優先で示し、取得失敗時に古い情報を現在の情報として扱わない。
- 情報誤りを見つけた場合は、開発用メモに「対象・出典URL・確認日・修正内容」を残してからパックを更新する。
- 将来公開する際は、データ利用規約、出典表示、プライバシー表示、問い合わせ窓口を別途整備する。

## 9. 実地テスト計画

| 項目 | 決定 |
| --- | --- |
| 代表地点 | 初期正式対応の確認は塔ノ岳、丹沢山、蛭ヶ岳、大山、表尾根の見晴らし地点、鍋割山周辺を基本とする。開発中のAR検証は、テストパックを用意した高尾・陣馬、奥多摩、箱根・富士山周辺、アルプスの一部等から、晴天と訪問機会に合わせて追加する。 |
| 確認観点 | 候補の有用性、方位ずれ、ラベルの重なり、遠方候補、遮蔽物、GPS／コンパス精度、ズームごとの表示。 |
| 記録方法 | 開発用診断モードでセンサー値・候補・手動補正を保存し、必要時だけスクリーンショットを添える。映像の常時保存はしない。 |
| 自宅での検証 | 現地ログのリプレイ、代表地点の疑似入力、固定テストデータによる自動テストを行う。 |
| MVP判定 | 自動テストと複数山域の現地ログで主要候補、精度低下、圏外、パック未導入時の動作を評価する。周辺機能の完成判定を天候待ちで停止しない。ただし初期正式対応の最終判定には、丹沢の代表地点を少なくとも1地点含む現地証拠を必要とする。 |

## 10. 後回しにする拡張

| 機能 | 採用する条件 |
| --- | --- |
| AI要約 | 情報カードが増え、登山前確認を短く整理したい実需が出た時。低コストモデルと利用上限を設定して導入する。 |
| Apple Watch | スマホを開かずに確認したい情報が、実地利用で明確になった時。山の同定はiPhoneが担当し、Watchは補助表示に限定する。 |
| Dynamic Island | ユーザーが開始したオフラインパックのダウンロード進捗など、時間が限られた処理を示す必要が出た時。 |
| クラウド同期 | 端末変更時のメモ・お気に入り引継ぎが必要になった時。 |
| 前日確認通知 | MVP後に登山予定日を登録できるようにした時。端末内のローカル通知だけを使い、前日18時を初期値とする。 |
| 気象の共有キャッシュ | App Store公開または複数ユーザー対応により、端末ごとのWeatherKit呼出しが利用枠・費用・安定運用へ影響すると見込まれる時。利用条件、帰属、加工・キャッシュ配信条件を再確認し、全山の一括巡回ではなくオンデマンド取得を基本とする。 |
| App Store公開 | 個人利用でデータ更新と実地精度が安定し、利用規約・出典・プライバシー・サポートを運用できると判断した時。 |

- [x] Debugビルドでは丹沢、高尾・陣馬、八ヶ岳、仙丈ヶ岳・南アルプス北部、男体山・日光連山、谷川岳・谷川連峰の6パックを一式として保存・削除できる。山頂候補は統合し、DEMは現在地を含む詳細範囲のパックへ自動切替する。単一パックを固定する起動引数は診断用として維持する。

## 12. 実装アーキテクチャ

| 項目 | 決定 |
| --- | --- |
| 全体方式 | **機能単位のレイヤードアーキテクチャ**を採用する。`Features`、`Domain`、`Infrastructure`、`DesignSystem`、`App` の責務を分ける。 |
| 画面の方式 | SwiftUIとObservationを使用する。単純で画面内だけの状態は `@State`、複数の非同期処理・キャンセル・状態遷移を持つ画面は `ScreenModel`、意味のあるView階層で共有する状態はEnvironmentを使用する。MVCのView Controllerは設けず、MVVMは必要な画面内の整理方法としてだけ利用する。 |
| 依存方向 | `View → ScreenModel → Domain` とする。`Infrastructure` はDomainが定義するプロトコルを実装し、AppのComposition Rootで組み立てる。DomainからSwiftUI、SwiftData、WeatherKit、Core Location、Core Motion、AVFoundationを参照しない。 |
| 依存注入 | アプリ起動時に `AppContainer` で具象実装を組み立て、イニシャライザーまたはSwiftUI Environmentで渡す。変更可能なグローバルシングルトンは使用しない。 |
| Xcode構成 | MVP開始時は、アプリ、ユニットテスト、UIテストの3ターゲットを基本とする。フォルダー境界を先に守り、必要性が確認できるまで多数のSwift PackageやFrameworkへ分割しない。 |
| 外部アーキテクチャ | TCA等の外部アーキテクチャライブラリは採用しない。Apple標準機能で不足する具体的な理由が生じた場合だけ再検討する。 |
| 実装粒度 | 一覧、検索、詳細などの小さな垂直スライス単位で、画面、状態、Domain、データ実装、テストを同時に追加する。形式だけのUseCaseや汎用層を先行作成しない。 |

## 13. MVP技術決定と初期値

ここに示す数値はMVPの実装・固定テストを開始するための初期値であり、安全基準や登山可否の判定値ではない。変更する場合は、基本設計書の値、固定テスト、実機または現地ログ、変更理由を同じ変更内で更新する。

### 13.1 保存方式

| 対象 | 決定 |
| --- | --- |
| 個人データ | SwiftData。行く前・山行中・行ったあとのメモ、お気に入り、手動の登頂済み状態、行きたい時期、確認リスト、最近見た山、よく使う出発駅、「気になった山」の記録メタデータ（選択した山、候補状態、記録日時、任意メモ、任意の視点位置、写真への参照）を保存する。登頂をGPSから自動判定しない |

| 山・施設・出典 | オフラインパック内の読み取り専用SQLite |
| 地形 | タイル単位でLZFSE圧縮した独自バイナリ。SQLiteに範囲、解像度、offset、length、ハッシュを持つ |

### 13.3 オフラインパック

- アプリ本体には、一覧・検索・基本詳細を利用できる軽量な `bootstrap.sqlite` を同梱する。丹沢の代表的な山には、今の時期の紹介に必要な季節メタデータも同梱する。カメラ候補と詳細地形に必要な丹沢パックは手動ダウンロードを基本とする。
- 配布単位は `manifest.json`、`manifest.sig`、`catalog.sqlite`、`terrain.lzfse` とする。MVPでは独自のZIP展開依存を追加しない。
- 内容版はSemantic Versioning、DBと地形の互換性は整数の `schemaVersion` で管理し、初期値をそれぞれ `1.0.0`、`1` とする。
- 全ファイルをSHA-256で検証し、`manifest.json` の生バイト列をEd25519で署名する。公開鍵だけをアプリへ含め、秘密鍵をリポジトリとアプリへ置かない。
- manifestには署名鍵の `keyID` を持たせる。鍵を変更する場合は先に新しい公開鍵を含むアプリを配布し、その後に新しい秘密鍵でパックを署名する。
- 一時領域へ取得し、署名、ハッシュ、サイズ、SQLite整合性、schemaVersion、必須レコードを検証してからディレクトリ単位で切り替える。
- 検証失敗時は一時データだけを破棄し、直前の正常なパックと個人データを保持する。
- 地形の入力は国土地理院の基盤地図情報数値標高モデルを使用し、利用可能な範囲でDEM5A、DEM5B、DEM5C、DEM10Bの順に優先する。開発用生成ツールは、同数値標高モデルを元に国土地理院が提供する256×256のPNGまたはテキスト標高タイルを取得済み原本として扱い、入力ファイルごとのSHA-256を記録してから変換する。DEM1Aは容量と効果を測定するまでMVPへ含めない。
- `terrain.lzfse` v1のheaderは固定16byteとする。byte 0〜3はASCII `YLTF`、4〜5はformat versionのUInt16、6〜7はheader sizeのUInt16、8〜11はtile countのUInt32、12〜15はflags／予約領域のUInt32とし、数値はlittle-endianで格納する。v1のheader sizeは16、flagsは0とし、未知の非0 flagsを拒否する。
- 国土地理院データを使用する場合は、取得元URL、取得日、利用条件、加工内容をSource Manifestへ記録し、アプリに出典と加工した旨を表示する。測量法上の申請要否と第三者権利はデータセットごとに確認する。

### 13.4 気象の鮮度と注意表示

- 山詳細を開いた時、前回取得から30分を超えていて通信可能なら更新を試す。手動更新は常に提供する。13.7節の1回の更新処理が全試行に失敗した後は、次の自動更新を同じ山について60秒以上空ける。
- 取得後1時間以内を「最新」、1時間超3時間以内を「更新を推奨」、3時間超を「古い情報」とする。古い値を削除や推測で置換せず、取得日時と公式情報への導線を表示する。
- WeatherKitの現在から12時間以内の予報風速10m/s以上を「風が強い予報」、15m/s以上を一段強い注意表示とする。気象庁の平均風速区分を初期値の参考にするが、測定条件が同一とは限らず、山上の安全を保証・判定しない。
- 現在から12時間以内の時間別予報で、WeatherKitが雷、雪・みぞれ・着氷性降水、または任意の3時間区間で5℃以上の気温低下を予報した場合は、事実と対象時間を注意カードへ表示する。
- WeatherKitの公式警報が取得できる場合は提供元、原文の意味、Appleが提供する詳細リンクを保持し、独自の安全判定へ変換しない。
- 注意項目を合算したスコア、「安全」「危険」「登山可能」の判定を作らない。
- WeatherKitの日別サマリーで、山頂座標における前の暦日の降水量、降雪量、最高・最低気温を取得できる場合は「前日の気象サマリー（山頂付近）」として表示する。直接観測した実績や登山道の状態とは表現しない。
- 前日の対象日は山頂地点のタイムゾーンで決める。対象日と取得日時を保存し、同じ対象日の取得から6時間以内はキャッシュを使用する。対象日が異なるキャッシュを前日の値として表示しない。
- 前日サマリーの取得失敗は現在・予報の表示を失敗扱いにしない。取得できない項目は「未取得」とし、降水なしや積雪なしへ置き換えない。
- 個人利用MVPでは、端末内キャッシュを利用して山詳細を開くたびの重複取得を避ける。正確な時刻でのバックグラウンド取得を前提にせず、画面表示時と明示更新時に上記の鮮度規則を適用する。
- 複数ユーザー対応時は、サーバー側の共有キャッシュを山IDと検証済み山頂座標の組で管理する。キャッシュ未作成または期限切れの山だけをWeatherKit REST APIから取得し、同じ山への同時要求は一つへまとめる。全国山頂索引、未配布山域、閲覧実績のない山を一律に定時取得しない。
- 定期的な先行更新を行う場合も、正式配布中の山域など運用対象を明示した集合に限定する。前日サマリーは、対象日の最初の閲覧または限定した先行更新で取得し、同じ対象日の正常値を共有する。
- 共有キャッシュのJSONはオフラインパックへ含めず、気象スナップショットとして別配信・別キャッシュにする。元データの対象時刻、WeatherKit取得時刻、共有キャッシュ公開時刻、提供元、帰属・警報詳細リンクを失わず、取得失敗時は直前の正常値を古い状態として保持する。
- 共有キャッシュの有効期間、先行更新間隔、対象山数、WeatherKit呼出し数、R2／配信基盤の読取り数と費用は別々に計測する。初期値は実測とWeatherKitの利用条件を確認してから正本文書と境界テストへ固定し、山数だけから全件巡回を開始しない。

### 13.5 山候補算出

| 項目 | 初期値 |
| --- | ---: |
| 検索最大距離 | 150km |
| カメラ上の最大ラベル数 | 5件 |
| 候補シートの最大件数 | 10件 |
| 水平位置精度 | 25m以下: 良好、25m超100m以下: 低下、100m超または負値: 無効 |
| 方位精度 | 10°以下: 良好、10°超25°以下: 低下、25°超または負値: 無効 |
| 垂直精度 | 30m以下: 良好、30m超75m以下: 低下、75m超または負値: 高度不使用 |
| 観測値の有効時間 | 位置15秒、方位・姿勢1秒。位置60秒超、方位・姿勢3秒超は候補重畳に使用しない |
| 画角境界の余白 | 水平・垂直とも3° |
| 有力候補 | score 0.75以上かつ精度低下なし |
| 通常候補 | score 0.50以上 |
| 候補シート掲載 | score 0.35以上 |
| 地形断面サンプリング | 目標間隔50m、1候補あたり最大512点 |
| 予測稜線 | 最大25km、方位2°間隔、各方位は目標100m間隔・最大256点 |
| 手動方位補正 | 左右それぞれ最大30°、単一タップは1°刻み、長押し中は1°刻みで連続補正、セッション終了で破棄 |
| ラベル位置の安定化 | 1pt以内は静止ノイズとして保持、64pt以上の変化は即時追従、中間は時定数0.30〜0.06秒で適応平滑化、観測間隔0.50秒超でリセット |

- 初期scoreは方位差45%、仰角差30%、観測品質15%、距離10%とし、各要素を0〜1へ正規化する。
- 方位は直近0.5秒の有効値を円周平均して表示の揺れを抑える。
- ラベルの画面座標は小さい揺れほど強く抑え、意図的な大きいパンには遅れず追従させる。手動方位補正、位置更新、センサー利用不能からの復帰では古い表示位置を引き継がない。
- 地形断面は現在地と山頂の間を目標50m間隔、最大512点で球面補間して取得する。遠方では点数上限を優先して間隔を広げ、カメラの毎フレーム処理とは分離して非同期に更新する。
- 地形が視線より30m以上高く見通しを遮る場合はscoreを0.75倍するが、DEM誤差を考慮して候補シートから即時削除しない。地形範囲外・高度不明・読み込み失敗は減点せず「地形未確認」として診断ログへ残す。
- 予測稜線は導入済みDEMから画角、手動補正上限、3°の余白を含む方位範囲を低頻度で計算する。姿勢更新ごとにDEMを再読込せず、生成済みの稜線を再投影する。DEM欠損区間は線で補完せず、詳細パック未導入・高度不明・読み込み失敗時は利用不能を明示する。
- scoreは内部順位付けにだけ使い、ユーザーには数値や確定結果として表示しない。
- 同点時は角度差、距離、安定したMountain IDの順で決定し、同じ入力から常に同じ結果を返す。

### 13.6 エラー分類

アプリ内の失敗は、発生元のフレームワーク名ではなく、利用者が次に取れる行動で次の5種類へ分類する。

| 分類 | 例 | 基本動作 |
| --- | --- | --- |
| 一時的な失敗 | 通信切断、タイムアウト、WeatherKitの一時障害 | 保存済み情報を維持し、規定回数だけ再試行できる |
| 利用者の操作が必要 | 権限拒否、容量不足、パック未導入 | 設定、パック管理、空き容量確保などの導線を示す |
| データ不正 | 署名・ハッシュ不一致、SQLite破損、未対応schema | 不正データを使用せず旧データを保持する。自動再試行しない |
| 機能制限 | 位置・方位精度低下、センサー利用不可 | 利用可能な範囲へ機能を縮退し、検索・手動選択へ切り替える |
| 内部不具合 | 想定外状態、保存処理の矛盾 | 個人データを初期化せず、安全な画面へ戻して診断可能にする |

下位層の原因は保持するが、利用者へ技術的なエラー文字列を直接表示しない。同じ原因でも状況に応じて表示、代替操作、再試行可否を変えられる型付きエラーとする。

### 13.7 タイムアウト、再試行、復旧

初期値は次とし、`NetworkPolicy` 等の設定値型へ集約する。

| 対象 | 初期値・方針 |
| --- | --- |
| WeatherKit | 1回15秒。タイムアウト、通信切断、一時的なサービス障害だけ2秒後に1回再試行する。両方失敗した後の自動更新は同じ山について60秒空ける |
| manifest等の小さいHTTP要求 | 1回15秒。一時的な通信失敗と5xx相当だけ2秒後に1回再試行する |
| パック本体 | Background URLSessionを使い、要求無通信30秒、処理全体2時間を初期値とする。通信回復時は中断位置からの再開を優先し、先頭からの自動再取得を繰り返さない |
| 同一要求 | 実行中の同一要求をまとめ、画面再描画や連打で重複通信を開始しない |
| 手動再試行 | 自動再試行の上限後も提供する。ただし実行中は重複開始しない |
| 再試行しない失敗 | 権限拒否、容量不足、キャンセル、署名・ハッシュ不一致、未対応schema、SQLite破損 |

- パック導入状態を `downloading`、`verifying`、`readyToInstall` として記録し、現在パックへの参照は検証完了後にだけ切り替える。
- 起動時に、OSの有効なバックグラウンドダウンロードへ対応しない一時領域を検査する。`readyToInstall` は再検証して切り替え、それ以外の孤立した一時領域は24時間後に削除する。
- SwiftDataを開けない場合もストア、WAL、SHMを自動削除・再作成しない。基本情報は読み取り専用データで継続し、個人データを利用できないことを表示する。初期化は、将来用意する明示操作と確認を経た場合だけ行う。

### 13.8 端末内データ保護

| 対象 | 保護・保存方針 |
| --- | --- |
| SwiftDataの個人データ | `NSFileProtectionComplete`。ストア本体だけでなくWAL、SHMと格納ディレクトリを同じ方針にする |
| 気になった山の写真 | `NSFileProtectionComplete`。アプリ専用領域に保持し、MVPではバックアップ対象外とする。明示保存した視点位置はSwiftDataの個人データとして同じ保護方針に従う |
| 明示保存した診断ログ・共有用一時ファイル | `NSFileProtectionComplete`。バックアップ対象外 |
| オフラインパック・導入一時領域・気象キャッシュ | `NSFileProtectionCompleteUntilFirstUserAuthentication`。再取得可能なためバックアップ対象外 |
| UserDefaults | 表示設定等の機密でない小さな設定だけ。メモ、位置、秘密情報を保存しない |
| 将来の秘密情報 | 必要になった場合だけKeychainへ保存し、初期値は `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`。iCloud Keychain同期を行わない |

MVPにはアプリ独自のパスワード、APIキー、アクセストークンを保存しない。オフラインパックの検証用公開鍵は秘密情報として扱わず、署名用秘密鍵は端末へ置かない。

### 13.9 通信と外部入力の防御

- 通信はHTTPSのみとし、App Transport Securityの例外、`NSAllowsArbitraryLoads`、独自の証明書信頼処理を追加しない。証明書ピンニングは運用上の失効リスクを避けるためMVPでは採用せず、パック内容はEd25519署名でも検証する。
- アプリ内WebViewで任意ページを表示しない。公式リンクは署名済みまたは同梱データから取得し、`https`、ユーザー情報なし、2,048文字以下を検証して外部ブラウザで開く。ブラウザは端末の既定を基本とし、Chromeが利用可能な場合または毎回選択を設定した場合にだけ選択肢を出す。
- 地図連携はApple Mapsの標準API／URLと、利用可能な場合のGoogle Maps公式スキームだけを許可し、文字列連結ではなく型または `URLComponents` で構築する。
- manifestは256KiB以下、署名は64byte、v1のファイルは `catalog.sqlite` と `terrain.lzfse` の2件だけ、パック総量は1,000,000,000byte以下（UI表示は1GB）とする。宣言サイズを超えた時点で受信を中止し、絶対パス、`..`、未知のファイル名を拒否する。
- SQLiteは検証後も読み取り専用かつ拡張読み込み無効で開き、データ由来の文字列をSQLとして実行しない。
- 地形タイルは展開後が256×256個のInt16、131,072byteであることを確認する。offset、length、加算のオーバーフロー、ファイル範囲外、想定外の展開サイズを拒否し、入力値をそのままメモリ確保量に使わない。
- schema v1の地形タイルは100,000件以下、1タイルの圧縮後サイズは262,144byte以下とする。タイルをoffset順に検証し、重複範囲、逆順、上限超過を展開前に拒否する。
- 将来の気象共有キャッシュは、WeatherKit秘密鍵と署名用トークンをアプリや公開R2オブジェクトへ含めない。アプリが受け取る気象JSONにはHTTPS、schema version、応答サイズ、山ID、座標範囲、日時、件数の上限を設け、実装時に正本文書とテストへ具体値を固定する。

### 13.10 Privacy Manifestと診断ログ

- Xcodeプロジェクト作成時に有効な `PrivacyInfo.xcprivacy` をアプリターゲットへ追加する。Required Reason APIを使用する変更では、Appleの最新の許可理由と実際の用途を同じ変更で記載し、追跡を行わない。
- App Store公開前にXcodeのPrivacy Report、App Store Connectのプライバシー回答、公開プライバシーポリシーを実装と照合する。個人利用MVPの段階でも、送信していないデータを送信済みとして扱わず、実際の通信を基準に記録する。
- 診断記録は初期状態で無効とし、明示的に開始・保存したものだけ端末内へ残す。未保存の観測値はセッション終了時に破棄する。
- Debugビルドの初期実装では、位置・方位・姿勢・投影条件・候補・手動方位補正を5Hzで最大5分記録する。記録開始時には直前10秒の軽量なメモリ内循環バッファを含めるが、保存操作をしない限りファイルへ残さない。カメラ映像は記録対象にしない。
- 保持指定していない診断ログは30日または20件の早い方を上限とし、削除予定を表示する。利用者は個別削除、全削除、必要なログの保持指定を行える。保持指定したログは自動削除しない。
- 共有は「匿名化サマリー」を既定とする。正確な座標を必要とするリプレイ用ログは、含まれる情報をプレビューし、別の確認操作を経た場合だけ書き出す。メモ本文、検索履歴、カメラ映像を自動で含めない。
- 共有用一時ファイルは共有完了・キャンセル後に削除し、削除できなかった場合も次回起動時または作成から24時間以内に削除する。

### 13.11 出発駅、外部経路、将来の通知

- MVPでは `SavedDeparturePoint` として「よく使う出発駅」を1件だけ登録できる。UI上は駅に限定するが、Domainでは名称と座標を持つ出発地点として、複数地点への拡張を妨げない。
- 駅検索はMapKitの検索を使い、検索語、駅名、座標、利用可能な地図識別子から利用者が候補を選ぶ。登録には通信が必要だが、登録済み駅はオフラインでも参照できる。検索語は保存しない。
- 「ここへ行く」では、出発地を「現在地」「よく使う出発駅」から毎回選択する。現在地はYamaLensが座標を取得して渡すのではなく、出発地を省略するか地図フレームワークの現在地項目を使い、地図アプリ側に委ねる。この操作のためだけにYamaLensの位置情報権限を要求しない。
- 登録駅を選んだ場合は駅と目的地の2地点を地図アプリへ渡す。地図アプリは設定でApple Maps（既定）、Google Maps（端末にインストールされている場合だけ）、毎回選択から選べる。移動手段も渡すが、経路、所要時間、運行状況はYamaLensで計算・保証しない。
- 立ち寄り検索は、検索地点名をMapKitで一時的に中心座標へ解決したうえで、カテゴリ（コンビニ、食事、温泉）と中心地点を外部地図アプリへ渡す。検索地点名、解決結果、検索履歴は保存・通常ログ出力せず、解決できない場合はカテゴリだけの検索へフォールバックする。
- 通知はMVPへ含めない。MVP後に登山予定日を登録する機能と一緒に、UserNotificationsのローカル通知として追加する。独自サーバー、APNsによるリモート通知、位置連動通知は使用しない。
- 前日確認通知は既定OFFとし、利用者が最初の通知を有効化した文脈で権限を要求する。初期時刻は予定日前日の18時で、予定変更・削除時は予約を更新・取消する。
- 通知は最新気象を内包・保証せず、通知をタップして対象の山詳細を開いた時に更新を試す。配信を安全機能や緊急警報として扱わず、拒否されても他機能を制限しない。

### 13.12 日照と施設情報

- 日の出・日の入りは山頂座標、対象日、地点のタイムゾーンから端末内で計算する。丹沢のタイムゾーンは `Asia/Tokyo`、標準的な大気差を含む太陽天頂角は90.833度を初期値とする。
- 計算結果は周辺の山や樹木による遮り、天候、現地照度を反映しない。そのため「山頂座標・今日」を明示し、安全な行動可能時間や登山可否へ変換しない。
- 施設はオフラインSQLiteへ保存し、種別、名称、任意座標、短い説明、HTTPSの公式URL、最終確認日、提供元を必須情報とする。営業期間、予約、収容人数、料金、営業時間、休業日、アクセス、運行主体等は確認済みの項目だけを施設の構造化属性として保存・表示する。自動取得した変動情報は、取得日時、取得方法、抽出規則の版を追跡可能にする。登山口にはアクセス施設と立ち寄り検索地点を明示的に関連付ける。店舗の営業情報・料金・運行状況を掲載する場合は確認日または取得日時を伴う事実として扱い、未確認値を推測しない。
- MVP初期データでは、丹沢中心6座（蛭ヶ岳、丹沢山、塔ノ岳、檜洞丸、鍋割山、大山）に代表的な山小屋、登山口、駐車場、公共交通、ケーブルカー、温泉を公式情報と確認日付きで整備する。施設IDは山名に依存しない安定IDとし、複数の山から同じ施設を参照できる。山と施設の関連には種類内の表示順を保持する。登録がない山は施設なしと断定せず「公式情報を確認中」と表示し、山名を外部地図で開く導線を提供する。
