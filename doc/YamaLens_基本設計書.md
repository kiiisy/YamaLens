# YamaLens 基本設計書

- 文書バージョン: 0.6
- 作成日: 2026-08-17
- 更新日: 2026-08-25
- 対象: iPhone 15 Pro／15 Pro Max および後継 Pro モデル
- 開発環境: Xcode 26
- 対応 OS: iOS 26 のみ（旧OSとの互換性は考慮しない）
- 初期対応エリア: 丹沢山地

## 1. 設計方針

YamaLens は、登山前および登山中に必要な周辺情報を確認するアプリである。ルート・登山地図・活動記録は扱わない。

核となる「カメラを向けて山を知る」機能は、画像をクラウドへ送信して判定するのではなく、iPhone の位置・方位・姿勢と、端末に保存した山データを照合して実現する。よって、対象山域を事前保存していれば圏外でも利用できる。

AI 要約は有料 API を伴うため、MVP の設計には依存させない。後から独立して追加できる構造にする。

## 3. 技術構成

| 区分 | 採用方針 | 用途 |
| --- | --- | --- |
| UI | SwiftUI | 一覧、検索、詳細、設定、カメラ画面の構築 |
| カメラ | AVFoundation | カメラプレビューの表示と、「気になった山」の明示撮影 |
| 位置・方位 | Core Location | 現在地、標高、真北基準の方位、精度情報 |
| 端末姿勢 | Core Motion | ピッチ・ロール等からカメラ視線を推定 |
| 個人データ | SwiftData | 行く前・山行中・行ったあとのメモ、お気に入り、手動の登頂済み状態、行きたい時期、確認リスト、最近見た山、よく使う出発駅、「気になった山」の記録メタデータ |
| 気になった山の写真 | Application Support配下のアプリ専用領域 | 記録ごとの撮影写真。SwiftDataには相対参照だけを保存し、パック・気象キャッシュ・写真ライブラリとは分離 |
| オフライン構造化データ | SQLite | 山、施設、登山口ごとのアクセス関係、出典、地形タイル索引。パック内では読み取り専用 |
| 大容量ファイル | LZFSE圧縮タイルを置くアプリ用ファイル領域 | 地形・標高データ、オフラインパック |
| 気象キャッシュ | アプリ用キャッシュ領域 | WeatherKit応答と取得日時。個人データとパックから分離 |
| ネットワーク | URLSession | 気象取得、オフラインパック更新 |
| 外部遷移 | Web URL | 公式情報を開く |
| アクセス案内 | Apple Maps / Google Maps URL | 現在地または利用者が登録した出発駅名から目的地への外部経路検索を開く |

データベース層は、画面・候補算出・通信処理から切り離す。将来、データ提供元や保存方式を変更しても影響を限定する。

### 3.1 アーキテクチャ

YamaLensは、SwiftUI向けの**機能単位のレイヤードアーキテクチャ**を採用する。MVCのView Controllerを中心にはせず、複雑な画面はMVVMに近い `View` と `ScreenModel` の組み合わせで整理する。ただし、すべての画面へ形式的に `ScreenModel` を作らず、永続化やセンサー処理まで集めない。

```text
View → ScreenModel → Domainのサービス／Repositoryプロトコル
                              ↑
             Infrastructureの具象実装

AppのComposition Root（AppContainer）が依存関係を組み立てる
```

| 区分 | 責務 | 依存してよい区分 |
| --- | --- | --- |
| `App` | アプリ起動、依存関係の組み立て、ルートタブ、画面遷移 | すべての区分 |
| `Features` | SwiftUI画面、画面状態、ユーザー操作、画面固有部品 | `Domain`、`DesignSystem` |
| `Domain` | 山、候補、鮮度等の値、純粋な計算、利用側が必要とするプロトコル | Swift標準ライブラリとFoundationの必要最小限 |
| `Infrastructure` | SwiftData、SQLite、WeatherKit、URLSession、位置・モーション・カメラ、外部地図のアダプター | `Domain`、Appleフレームワーク |
| `DesignSystem` | 色、文字、余白、再利用UI部品 | SwiftUI。`Features` と `Infrastructure` には依存しない |

- Viewだけで完結する表示切り替えや入力途中の値は `@State` とし、別の参照型を作らない。
- 複数の非同期処理、キャンセル、画面状態遷移を持ち、Viewから分離してテストする価値がある場合は、`@MainActor` とObservationの `@Observable` を使用した `ScreenModel` を置く。
- 複数画面または意味のあるView階層で共有する状態だけをEnvironmentで渡す。画面固有の状態やすべてのサービスを無条件にEnvironmentへ登録しない。
- Domainはフレームワーク非依存の値型を基本とし、候補算出をセンサーなしの固定入力でテストできるようにする。
- Repository等のプロトコルは利用側であるDomainに置き、具象実装をInfrastructureに置く。
- 意味のある複数処理を調整する場合だけDomainサービスまたはUseCaseを作る。ボタン操作ごとに形式的な型を作らない。
- TCA、RxSwift等の外部アーキテクチャ・状態管理ライブラリはMVPでは使用しない。

保存場所は次のように分ける。

- 同梱 `bootstrap.sqlite` はアプリBundle内で読み取り専用とする。
- 検証済みオフラインパックはApplication Support配下に置き、再取得可能なためiCloud／端末バックアップ対象から除外する。
- WeatherKit応答はCaches配下に置き、OSに削除され得る前提で扱う。
- SwiftDataの個人データはApplication Support配下に置き、通常の端末バックアップ対象とする。パック削除処理から参照・削除しない。
- 「気になった山」の写真はApplication Support配下のアプリ専用領域に置き、`NSFileProtectionComplete` とする。MVPではバックアップ対象外とし、写真ライブラリへ自動保存しない。
- MVP後に追加する自動ダウンロード、容量上限等の小さな設定値はUserDefaultsへ保存する。メモ本文をUserDefaultsへ置かない。

## 4. 機能別設計

### 4.1 山一覧・検索

- アプリ起動時はホーム（山一覧）を表示する。カメラ機能を利用しない場合も、すべての山情報へ到達できる。
- セクションは「お気に入り」「最近見た山」「オフライン保存済み」「丹沢の山」とする。
- 検索対象は名称、別名、山域、都道府県、標高帯。
- 検索結果から山詳細画面へ遷移する。
- 位置情報を許可している場合のみ「近い順」を提供する。未許可でも検索・閲覧に支障は出さない。

### 4.2 カメラ山候補表示

#### 入力

- 現在地: 緯度、経度、標高、水平精度、垂直精度。
- 向き: 真北基準の方位、方位精度。
- 姿勢: 端末のピッチ・ロール・ヨー。
- カメラ情報: 利用カメラ、画角、端末の画面向き。
- ズーム状態: 倍率と使用中レンズ。倍率・レンズが変わるたびに有効画角を更新する。
- オフラインパック: 山頂の座標・標高・名称、必要に応じて地形・標高データ。

#### 処理

1. 現在地から、オフラインパック内の各山頂への距離・方位・仰角を算出する。
2. カメラの水平・垂直画角に入る山を一次候補として抽出する。
3. 距離、視線との角度差、仰角、方位・位置精度を用いて候補の一致度を算出する。
4. 地形データが利用可能な場合は、現在地から山頂までの見通しを確認し、明らかに稜線の裏となる候補を抑制する。
5. 予測稜線を表示する場合は、画角周辺のDEMから各方位の最大仰角を低頻度で生成する。
6. ズーム倍率と使用中レンズの画角から、各候補と生成済み予測稜線の画面上の位置を再投影する。
7. 一致度の高い候補をカメラ映像に重ね、山名・標高・距離・方角を表示する。

#### 出力・UI

- 各候補は「候補」として表示し、タップで山詳細を開く。
- 一致度の数値は原則表示せず、「有力」「候補」などの段階表現を用いる。
- 水平精度、方位精度、または姿勢が一定基準を満たさない場合は、候補を確定的に見せず「精度が低下しています」と表示する。
- 磁気干渉時のキャリブレーション案内と、検索・一覧へ戻る導線を常に表示する。
- 処理は端末内で完結し、カメラ映像・位置情報を外部へ送信しない。
- 予測稜線は既定で表示し、カメラ画面と設定から表示・非表示を切り替えられる。DEM欠損区間を推測で接続せず、詳細パック未導入等で生成できない場合は理由を表示する。
- MVPでは `1×`、`2×`、`3×` の段階的なズームを提供する。連続ピンチズームと端末ごとのレンズ自動切替の細かな最適化は、実機検証後に追加する。

#### 候補算出の初期パラメーター

初期値は事前決定事項13.5節を正とし、`CandidateTuning.default` のような一つの値型へ集約する。画面、センサーアダプター、順位付け関数へ数値を散在させない。

- 最大150km以内を検索し、score 0.50以上の上位5件をカメラへ、score 0.35以上の上位10件を候補シートへ出す。
- scoreは方位差45%、仰角差30%、観測品質15%、距離10%を初期重みとする。方位差と仰角差は実際の水平・垂直画角と3°の境界余白で正規化する。
- 水平位置精度25m以下、方位精度10°以下、垂直精度30m以下を良好とする。Core Locationが負値を返した場合は無効値として扱う。
- 水平位置精度100m超または方位精度25°超では、カメラへの候補重畳を停止し、精度低下と検索導線を表示する。高度だけが無効な場合は仰角要素を除外して品質を下げ、0mで代用しない。
- 位置観測は15秒以内、方位・姿勢は1秒以内を通常入力とする。位置60秒超、方位・姿勢3秒超は候補重畳へ使用しない。
- score 0.75以上でも観測品質が低下している場合は「有力候補」と表現しない。score自体は表示しない。
- 地形が視線より30m以上高い場合は遮蔽ペナルティを適用するが、候補を削除せず候補シートに残す。
- 地形断面は目標50m間隔、1候補あたり最大512点を球面上で補間する。位置または候補の変化時に非同期で読み込み、姿勢更新のフレームループを待たせない。
- 予測稜線は最大25km、方位2°間隔、各方位は目標100m間隔・最大256点で生成する。現在地または画角中心が大きく変わった場合だけ非同期で再生成し、通常の姿勢追従と手動方位補正では既存結果を軽量に再投影する。
- ラベル座標は候補算出後にMountain ID単位で適応平滑化する。1pt以内の微振動は保持し、64pt以上の移動は即時追従し、その中間だけ移動量に応じて時定数0.30〜0.06秒で補間する。0.50秒を超える観測断、位置更新、手動方位補正、センサー利用不能時には状態をリセットする。
- パラメーター変更は、固定境界テストと既存の現地リプレイを通し、改善した地点と悪化していない地点を記録してから行う。

scoreの初期計算は次とする。`clamp` は0〜1へ丸め、角度差は北の境界をまたいで最短角へ正規化する。

```text
bearingScore  = clamp(1 - abs(bearingDifference) / (horizontalFOV / 2 + 3°))
elevationScore = clamp(1 - abs(elevationDifference) / (verticalFOV / 2 + 3°))
distanceScore = clamp(1 - distance / 150km)
score = 0.45 * bearingScore
      + 0.30 * elevationScore
      + 0.15 * observationQualityScore
      + 0.10 * distanceScore
```

- 水平位置qualityは25m以下を1.0、25〜100mを1.0から0.4へ線形補間、100m超または負値を0とする。
- 方位qualityは10°以下を1.0、10〜25°を1.0から0.4へ線形補間、25°超または負値を0とする。
- 垂直qualityは30m以下を1.0、30〜75mを1.0から0.6へ線形補間、75m超または負値を0.6とし、高度不使用を別理由として残す。
- 鮮度qualityは、位置15秒以下、方位・姿勢1秒以下を1.0とする。位置15〜60秒、方位・姿勢1〜3秒をそれぞれ1.0から0.4へ線形補間し、それを超えた値を0とする。
- `observationQualityScore` は、水平位置、方位、垂直、各観測鮮度qualityの最小値とする。水平位置または方位が0なら候補重畳を停止する。
- 高度だけが無効な場合は `elevationScore` を中立値0.5、`observationQualityScore` の上限を0.6とする。高度0mを仮定しない。
- 地形遮蔽が判定された場合は最終scoreを0.75倍する。遮蔽判定不能の場合はペナルティを適用せず、診断理由へ「地形未確認」を残す。

### 4.3 山詳細ダッシュボード

縦スクロール画面とし、情報の鮮度が高いものを上部に置く。

1. ヘッダー: 山名、標高、現在地からの距離・方角、お気に入り。
2. 登山前チェック: 気象の注意、情報取得時刻、公式情報への導線。
3. 天気・日照: 気温、風速・風向、降水、雲量、降雪・雷情報（取得可能なもの）、日の出・日の入り。
4. 山小屋: 営業期間、予約要否、連絡先、公式リンク、最終確認日。
5. アクセス: 登山口、駐車場、公共交通、ロープウェイ、温泉、各公式リンク。
6. 個人メモ: 自由メモ、行きたい時期、確認リスト。
7. 山詳細写真: 既定イラストまたは、SwiftDataで端末内へ保存する山ごとのユーザー選択写真。選択写真はホーム等の山カードと山詳細へのズーム遷移でも同じデータを使用する。
8. 外部導線: 公式サイト、地図アプリでのアクセス検索、検証済みURLがある場合のYAMAP山ページ。

通信がない場合、更新情報の代わりに保存済みの内容と最終取得時刻を表示する。

#### 出発地を選べる外部アクセス

- 各登山口・駐車場・駅・バス停を、緯度経度を持つ `PointOfInterest` として保存する。
- 設定で「よく使う出発駅」を1件だけ登録できる。JR・私鉄・地下鉄を含む、地図アプリで検索できる正式名称を利用者が入力し、`SavedDeparturePoint` には種別、外部地図で使う正式名称、更新日時を保存する。入力値は前後の空白を除去し、空文字は保存しない。検索履歴は保存しない。
- 登録済み駅はSwiftDataへ保存するため、圏外でも名称を確認できる。駅の入力・変更・削除に通信は必要ない。
- 登山口アクセスで「公共交通」または「車」を選んだ後、バス停・ケーブルカー・駐車場の「地図を開く」をタップすると、その施設を目的地、選択済みアクセス手段を移動手段として固定した経路sheetを開く。経路sheetは目的地、出発地、実行ボタンだけを表示し、移動手段の表示・再選択は行わない。
- 経路sheetでは出発地を「現在地」「よく使う出発駅」から選び、実行ボタンで設定済み地図アプリを開く。登録駅は保存済みの正式名称を外部地図の出発地検索語として渡し、未登録の場合は同じ画面に設定への登録導線を表示する。地図アプリ設定が「毎回選択」の場合だけ、実行ボタンの後に地図アプリの確認ダイアログを表示する。
- 「現在地」はYamaLensがCore Locationで座標を取得して渡さず、Apple Mapsでは目的地1件または現在地MapItem、Google Mapsではorigin省略として地図アプリ側へ委ねる。この操作だけを理由にYamaLensの位置情報権限を要求しない。
- 登録駅では、利用者が保存した正式名称を出発地検索語として、目的地とともに地図アプリ用URLへエンコードして渡す。任意URLは外部アプリへ渡さない。
- 地図アプリの選択肢はAppleマップを標準とし、Google Mapsが端末にインストールされている場合は選択肢に追加する。選択結果は端末内設定へ保存し、「毎回選択」も選べる。
- 公式サイトは端末の既定ブラウザで開く。Chromeが端末にインストールされている場合はChromeも選択でき、選択結果または「毎回選択」を端末内設定へ保存する。Safariを個別に指定しない。
- YAMAPはパックに保存した `https://yamap.com/mountains/<ID>` をSwiftUIの外部Linkとして開く。Universal Linkの関連付けはYAMAP側へ委ね、インストール済みならアプリ、未導入ならWebへフォールバックする。非公開URL schemeや未文書化の計画作成パラメータは組み立てず、対象山ページからYAMAP側の計画作成操作へ進んでもらう。
- 立ち寄り検索では、オフラインデータ上の検索地点名をMapKitで一時的に中心座標へ解決し、検索カテゴリと中心座標を別パラメータとして外部地図アプリへ渡す。解決結果や検索履歴を保存・通常ログ出力せず、解決失敗時はカテゴリのみを渡す。
- 車、徒歩、公共交通の選択は地図アプリへ渡す。YamaLensは経路、所要時間、運行状況を独自に計算・保証しない。
- YamaLensの位置情報を拒否していても両方の選択肢を利用できる。外部地図が現在地を利用できない場合の案内は地図アプリ側に委ねる。
- 圏外では外部地図で経路を取得できない可能性を表示しつつ、保存済みの目的地名・座標・登録駅・公式アクセス情報は閲覧可能にする。地図アプリのオフライン可否をYamaLensで断定しない。

### 4.4 オフラインパック

- アプリには一覧・検索・基本詳細用の軽量なbootstrapデータを同梱する。詳細地形を含む初期パックは「丹沢山地」だけとし、Cloudflare R2の独自ドメインによる静的HTTPS配信から、初回起動時または設定画面で利用者が明示してダウンロードする。
- パックには、山頂データ、別名、山域、登山口・山小屋等の基本情報、必要な地形・標高データを含める。
- 気象はパックへ含めず、端末キャッシュとして分離する。施設の営業・運行情報は最終確認日と公式URLを持ち、最新状態を保証しない。
- パックはバージョン、容量、作成日、更新日を持つ。個人利用MVPでは手動更新だけを提供する。
- 詳細パックが未保存でもbootstrapの一覧・検索・基本詳細を提供するが、カメラ候補表示は利用不可または限定モードにする。
- ユーザーはパック一覧から追加・更新・削除できる。パック削除時も、個人メモ・お気に入り・気になった山の記録と写真は保持する。
- 自動ダウンロード、近隣山域の提案、モバイル通信の選択は個人利用MVP後に追加する。追加時は自動ダウンロードを初期値オフとし、Wi-Fi時のみを初期値とする。
- 大容量パックは、ユーザーが開始したダウンロードをバックグラウンドでも継続できるようにする。ただしiOSのバックグラウンド実行はシステム管理であるため、完了時刻を保証する前提にはしない。

#### オフラインパックの設定

| 設定 | 初期値 | 内容 |
| --- | --- | --- |
| 配布地域 | 丹沢のみ | 個人利用MVPでは、丹沢以外を利用者向けの保存候補として表示しない。 |
| 配布元 | Cloudflare R2 | Standardストレージを独自ドメインのHTTPS URLで公開する。アプリには読取り用URLだけを持ち、R2の書込み認証情報は含めない。 |
| 手動更新 | 有効 | ユーザー操作でmanifestを確認し、更新があれば署名・整合性検証後に切り替える。 |
| 自動ダウンロード | MVP後 | 追加時は初期値オフ、Wi-Fi時のみを初期値とし、モバイル通信は明示許可にする。 |

個人利用MVPでは丹沢パックだけを手動で管理し、容量不足時もアプリが無断で削除しない。複数地域・自動保存を追加した後は、古く使用頻度の低い自動保存パックを削除候補として提示する。

#### パック形式と検証

アプリ本体には `bootstrap.sqlite` を同梱し、パック未導入・圏外でも丹沢の一覧、検索、基本詳細を利用可能にする。詳細地形を含む丹沢パックは、Cloudflare R2の独自ドメインによる静的HTTPS配信元から次のファイルを一時ディレクトリへ取得する。R2の書込み用APIトークン、S3認証情報、Ed25519秘密鍵はMac上の生成・アップロード工程だけで扱い、アプリへ含めない。

`bootstrap.sqlite` は `Data/Bootstrap/tanzawa-bootstrap-v1.json` を入力として、`Tools/OfflinePackageBuilder/build_bootstrap.py` で生成・検証する。アプリはBundle内のDBを読み取り専用で開き、`integrity_check`、schemaVersion、必須の山レコードを確認してから利用する。開発用データは丹沢の中心6座と、富士山等の周辺候補11座を区別して収録する。正式な配布データとする前に `Data/SourceManifests/tanzawa-bootstrap-v1.yaml` に従って国土地理院の一次情報との照合と利用手続の確認を完了する。

```text
tanzawa/1.0.0/
├─ manifest.json
├─ manifest.sig
├─ catalog.sqlite
└─ terrain.lzfse
```

- `manifest.json` は `packageID`、`contentVersion`、`schemaVersion`、作成日時、対象範囲、最小アプリ版、各ファイルのbyte数・SHA-256、Source Manifest IDを持つ。
- `manifest.sig` は配布された `manifest.json` の生バイト列に対するEd25519署名とする。改行やキー順を変換してから検証しない。
- `keyID` でアプリ内の検証用公開鍵を選択する。未知の鍵を信頼せず、鍵更新は新しい公開鍵を含むアプリ更新を先に配布してから行う。
- `catalog.sqlite` は山、施設、出典、地形タイルの範囲・解像度・offset・length・ハッシュを持ち、アプリから読み取り専用で開く。
- `terrain.lzfse` はタイルごとに独立してLZFSE圧縮し、必要なタイルだけを展開できるようにする。
- 初期 `contentVersion` は `1.0.0`、`schemaVersion` は `1` とする。内容更新と読み取り互換性を別に管理する。
- 署名、全ファイルのSHA-256とサイズ、SQLiteの `integrity_check`・外部キー、schemaVersion、必須テーブル・必須レコードを検証する。
- 検証完了後だけ現在パックへの参照をアトミックに切り替える。失敗時は一時ディレクトリだけを破棄し、旧パックとSwiftDataを保持する。
- 署名秘密鍵はリポジトリ、アプリ、通常CIへ置かない。検証用公開鍵だけをアプリへ含める。

`manifest.json` v1は次の構造とし、UTF-8、JSON、時刻はUTCのRFC 3339、ハッシュは小文字16進数で生成する。`manifest.sig` は64byteの生署名とする。

```json
{
  "formatVersion": 1,
  "packageID": "jp.kanagawa.tanzawa",
  "contentVersion": "1.0.0",
  "schemaVersion": 1,
  "signatureAlgorithm": "Ed25519",
  "keyID": "yamalens-pack-2026-01",
  "createdAt": "2026-08-18T00:00:00Z",
  "minimumAppVersion": "0.1.0",
  "bounds": {
    "north": 0.0,
    "south": 0.0,
    "east": 0.0,
    "west": 0.0
  },
  "sourceManifestIDs": ["gsi-dem-tanzawa-v1"],
  "files": [
    {
      "path": "catalog.sqlite",
      "byteCount": 0,
      "sha256": ""
    },
    {
      "path": "terrain.lzfse",
      "byteCount": 0,
      "sha256": ""
    }
  ]
}
```

数値の0と空文字は構造例のプレースホルダーであり、配布パックでは実値を必須とする。未知の必須 `formatVersion` または `schemaVersion` は読み込まず、対応アプリ版への更新を案内する。

`catalog.sqlite` schema v1は次のテーブルを持つ。

| テーブル | 主な列・制約 |
| --- | --- |
| `package_metadata` | `key TEXT PRIMARY KEY`、`value TEXT NOT NULL` |
| `regions` | `id TEXT PRIMARY KEY`、`name TEXT NOT NULL`、`prefecture_name TEXT NOT NULL` |
| `mountains` | `id TEXT PRIMARY KEY`、`region_id`、`canonical_name`、`search_name`、`coverage_role`（`core`／`surroundingCandidate`）、`latitude`、`longitude`、`elevation_m`、任意の`yamap_url`、`updated_at` |
| `mountain_names` | `mountain_id`、`name`、`search_name`、`kind`。`PRIMARY KEY(mountain_id, name)` |
| `points_of_interest` | `id TEXT PRIMARY KEY`、`region_id`、`type`、`name`、任意座標、`summary`、`official_url`、`checked_at` |
| `point_of_interest_details` | `point_of_interest_id`、`kind`、`value`、`display_order`。営業期間、予約、収容人数、料金、営業時間、休業日、アクセス、運行主体等の確認済み属性 |
| `mountain_points_of_interest` | `mountain_id`、`point_of_interest_id`、`display_order`。複合PRIMARY KEY。施設IDは山名に依存せず、同じ施設を複数の山から参照できる |
| `trailhead_access_points` | `trailhead_id`、`point_of_interest_id`、`display_order`。登山口と駐車場・交通・代表的な温泉の関連 |
| `trailhead_search_areas` | `id TEXT PRIMARY KEY`、`trailhead_id`、`name`、`display_order`。登山口または最寄り駅周辺を外部地図で検索する地点 |
| `source_links` | `id TEXT PRIMARY KEY`、`provider`、`title`、`url`、`license_url`、`checked_at`、`is_primary`、`attribution_text`、`processing_note` |
| `entity_sources` | `entity_type`、`entity_id`、`source_id`。複合PRIMARY KEY |
| `terrain_tiles` | `id TEXT PRIMARY KEY`、境界、解像度、行列数、`offset_bytes`、`compressed_bytes`、`uncompressed_bytes`、`sha256` |

- 外部キーを有効にし、ID、検索名、山域、施設種別、地形範囲に必要なindexを作る。
- `points_of_interest.checked_at` と `source_links.checked_at` は、人が確認したデータでは最終確認日時、自動取得したデータでは検証済み取得日時を表す。取得方法と抽出規則の版は対応するSource Manifestで追跡する。
- `point_of_interest_details` は施設カテゴリを増やすものではなく、施設詳細内で確認済みの属性を個別表示するために使用する。未確認の属性は行を作らず、同じ施設内で `kind` を重複させない。テーブルを持たない既存schema v1パックは詳細属性なしとして互換読込する。
- `mountain_points_of_interest.display_order` は同じ施設種別内の表示順として使用する。列を持たない既存schema v1パックは名称順へフォールバックして互換読込する。
- schema v1初期版の詳細パックは `trailhead_access_points` と `trailhead_search_areas` の両方を持たない場合に限り、登山口アクセス関係が未収録の旧版として互換受理する。片方だけ存在する不完全なパックは拒否する。施設アクセス表示は同梱bootstrapまたは両テーブルを持つ更新版を使用する。
- `mountains.yamap_url` は人が対象山との対応を確認した `https://yamap.com/mountains/<正の整数ID>` だけを許可する。生成時にscheme、host、path、query、fragmentを検証し、アプリ読込時にも同じ形式以外は導線へ渡さない。既存のschema v1パックに列がない場合はリンクなしとして互換読込する。
- 山名検索は `search_name` に、大文字小文字、全角半角、ひらがな・カタカナ、空白を正規化した値を保存する。MVPでは外部検索ライブラリやFTSを必須にせず、実測で必要になった場合だけ追加する。
- `terrain.lzfse` は固定16byteのheaderと、個別にLZFSE圧縮した256×256の標高タイルで構成する。headerはASCII `YLTF`（byte 0〜3）、format version UInt16（4〜5）、header size UInt16（6〜7）、tile count UInt32（8〜11）、flags UInt32（12〜15）のlittle-endianとする。v1はversion 1、header size 16、flags 0とし、未知のflagsを拒否する。標高値は1m単位の符号付き16bit整数、欠損値は `-32768` とする。
- タイルの境界、格子間隔、offset、圧縮前後サイズ、展開後SHA-256は `terrain_tiles` を正とし、範囲外読み込みを拒否する。
- schema v1では地形タイルを100,000件以下、各タイルの圧縮後サイズを262,144byte以下とし、offset順で重複していないことを展開前に確認する。
- `Tools/OfflinePackageBuilder/build_detailed_pack.py` は、取得済みの国土地理院256×256 PNG／テキスト標高タイルを `z/x/y.png`／`z/x/y.txt` 構成で受け取る。最初にデータ種別・相対パス・原本SHA-256を持つ入力索引を生成し、ビルド時に原本の不変性を再確認する。ズーム15の同一セルはDEM5A、DEM5B、DEM5Cの順で補完し、残る欠損は索引に存在するズーム14の親DEM10Bを2×2の最近傍展開で補う。小数標高は1m単位で四捨五入する。取得計画・明示的な取得・パック生成を別コマンドとし、Source Manifestの取得日・元データ版・利用条件確認と分離する。
- 生成ツールはタイルごとのLZFSE往復、SQLite整合性、地形offset・サイズ・SHA-256、Ed25519署名を自己検証し、すべて成功した場合だけ完成ディレクトリを出力する。既存出力を暗黙に上書きせず、秘密鍵はコマンド引数でリポジトリ外のファイルを渡す。
- 導入時は一時領域で署名・manifest・2ファイル・SQLite・全地形タイルを検証し、`Versions/<contentVersion>` へ移動した後に小さな `active-version` をatomic書き換えして参照を切り替える。切替前の版は保持し、`readyToInstall` journalが残った場合は起動時に再検証してから切替を完了する。

#### 容量予算（設計目標）

全国の高解像度地形データを端末に入れる設計にはしない。全国の軽量な山頂索引と、利用頻度の高い山域だけの多段階地形データを組み合わせる。

| データ | 容量の目安 | 方針 |
| --- | ---: | --- |
| アプリ本体 | 50〜100MB | UI、候補算出、端末内計算ロジック。写真・地図画像は同梱しない。 |
| 全国の軽量山頂索引 | 10〜30MB | 名称、別名、座標、標高など。遠方の山を候補に残すために使う。 |
| 丹沢の施設・公式リンク | 1〜10MB | 山小屋、登山口、駐車場、温泉、出典情報。 |
| 丹沢詳細パック | 100〜300MB | 近距離を高解像度、遠距離を低解像度にした地形・標高データ。 |
| 気象キャッシュ・個人メモ | 通常は数MB以下 | 気象キャッシュには上限・自動削除方針を設ける。気になった山の写真は利用者が削除するまで自動削除しない。 |

初回の実用的な構成は、**合計150〜400MB程度**を目標とする。1GBを超えないことを初期の容量目標とし、実データを使った試作で測定して調整する。

丹沢から遠く見える山を扱うため、地形は一律の解像度にしない。丹沢周辺は5〜10m程度の詳細データ、より遠い範囲は50〜250m程度の粗いデータ、全国は山頂索引のみ、という段階構成にする。これにより数GB規模の全国高解像度パックを避ける。

### 4.5 個人データ

- メモ、お気に入り、行きたい時期、確認リスト、最近見た山を端末内へ保存する。
- ユーザーが削除したメモ・お気に入りは直ちに一覧・詳細から除外する。
- 「気になった山」は、AR候補を選択してから利用者が明示的に撮影・保存する記録である。選択した `MountainID`、候補として選択した時点の品質情報、撮影日時、任意メモ、写真への相対参照を保存する。
- 正確な視点位置は既定で保存しない。利用者が記録ごとに明示して有効化した場合だけ、座標、水平精度、取得日時を保存する。保存の有無によって撮影・記録を妨げない。
- 記録を削除すると、関連する写真、任意メモ、保存済み視点位置を同時に削除する。削除前に対象を表示して確認を求め、オフラインパックの削除処理からは変更しない。
- MVP ではアカウント作成・クラウド同期を実装しない。

### 4.6 今の時期の丹沢・近い山

- 「今の時期の丹沢」は `bootstrap.sqlite` の丹沢代表山と固定の季節メタデータだけから求める。詳細オフラインパック、通信、現在地、WeatherKitの値は入力にせず、登山可否・安全性の順位付けをしない。
- 季節メタデータは山ごとの紹介期間、短い紹介理由、編集上の優先度、重複を避ける山域グループを持つ。中心期間の山を優先し、件数不足時だけ前後の紹介期間を補い、優先度と安定したMountain IDで決定的に並べる。ホームでは最大4件を表示する。
- 「近い山」は、位置情報の有効な観測値と、正式対応済みまたは同梱済みの基本情報を持つ山だけを対象に、150km以内を距離順で最大10件表示する。季節紹介の順位付けに位置を混ぜない。
- 近い山の候補が0件の場合、遠い山や未対応地域の山を代替表示しない。「近い山は対応地域にありません。現在は丹沢を中心に収録しています」と、山名検索への導線を返す。

## 5. データ設計

### 5.1 主要データ

| データ | 主な属性 | 保存場所 |
| --- | --- | --- |
| Mountain | ID、名称、別名、座標、標高、山域、任意の季節紹介メタデータ | `bootstrap.sqlite` またはオフラインパック DB |

### 5.2 データ更新

- 山頂・地形・施設データは、オフラインパックの更新で差し替える。
- 今の時期の丹沢に使う季節メタデータは、`bootstrap.sqlite` の同梱データとして更新する。気象の取得値や利用者の現在地から自動更新しない。
- 現在・予報の天気は、通信可能時に山詳細画面表示またはユーザー操作で更新する。
- 前日サマリーは、山頂地点のタイムゾーンにおける前の暦日を対象にWeatherKitから取得する。同じ対象日の取得から6時間以内はキャッシュを利用し、日付が変わった場合は別対象として取得する。
- 山小屋・交通等の変動情報は、公式 URL と最終確認日を優先して表示する。
- 更新に失敗しても、旧データを削除せず、最終取得時刻を明示して表示する。
- 日の出・日の入りは山頂座標、対象日、地点のタイムゾーンから端末内で計算する。丹沢では `Asia/Tokyo` を使用し、標準的な大気差を含む太陽天頂角90.833度を初期値とする。周辺地形による遮蔽や現地照度は計算結果へ含めない。
- 施設レコードは種別、名称、任意座標、短い説明、HTTPSの公式URL、最終確認日、提供元を持つ。自動取得した変動情報は取得日時、取得方法、抽出規則の版をSource Manifestから追跡可能にする。登山口とアクセス施設、立ち寄り検索地点は明示的な関連テーブルで結ぶ。SQLite読込時にもURL、日付、種別、座標範囲を検証し、不正なレコードを画面へ渡さない。

施設情報の自動取得は、次の生成側パイプラインとして段階導入する。

このパイプラインの「人手レビュー／承認」はアプリ利用者向け機能ではなく、オフラインパックを作成・配布する開発・運用担当者がリポジトリ上で実施する公開前工程である。承認待ちの候補データをアプリへ配布せず、アプリは検証・生成済みのパックだけを読み込む。

1. Source Manifestで承認済みの公式情報源だけを取得対象にする。情報源ごとに取得方式、利用条件・robots.txtの確認結果、取得間隔、許可する抽出項目、専用抽出規則の版を持つ。
2. 取得した原文または構造化応答を作業用領域へ保存し、取得日時、最終URL、HTTP状態、本文SHA-256を記録する。アプリへ原文を配布しない。
3. 情報源専用の抽出規則で候補値へ変換し、型、文字数、日付、座標、HTTPS URL、件数上限を検証する。取得できない項目を推測で補完しない。
4. 現行の検証済みJSONとの差分を作り、新規施設、削除候補、抽出規則変更、大幅な値変化、営業・通行に関する曖昧な文だけを人手確認待ちにする。確認されていない候補値は正本JSONへ自動反映しない。
5. 人手レビューでは候補ファイルのSHA-256、全候補項目の採否と理由、公式根拠URL・確認日、反映前の対象値、反映後の内容版を記録する。適用処理は候補と反映前データがレビュー時点から変わっていないことを検証し、承認済みの許可項目だけを新しいJSONへ出力する。出力差分を確認して正本JSONへ反映し、既存のSQLite生成・整合性検証・署名済みパック生成へ渡す。差分がなければ内容版を更新しない。
6. 取得、抽出、検証、署名のいずれかに失敗した場合は、公開中のパックと直前の正常値を保持する。アプリは既存のパック更新導線で検証済み内容だけを受け取る。

MVPでは更新頻度を低く保ち、施設情報の変更も既存の `catalog.sqlite` を含む山域パックの内容版更新として配布する。施設更新だけで大きな地形ファイルを再取得する負担が実測で問題になった場合に、Info Overlayを独立署名・独立ロールバックできるパック形式へ改定する。自動取得の開始条件として先に配布形式を分割する必要はない。

最初の取得パイロットは、神奈川県オープンデータ「公園データ一覧」の公式CKAN APIにある秦野戸川公園1件だけを対象とする。地方公共団体名と公園名の完全一致filter、許可項目、応答サイズ、取得間隔、抽出規則の版を設定ファイルへ固定し、既存の `hadano-tokawa-okura-parking` との人手確認用差分まで生成する。レビュー適用は候補SHA-256、全項目の採否、公式ページの確認結果、反映前データ、内容版の更新を検証する。正本JSONの自動変更、HTML巡回、定期スケジュール実行はこのパイロットに含めない。

自動取得候補が存在しない既存施設についても、初回整備時に全施設・全情報源を一括レビューする。レビュー記録は正本JSON全体のSHA-256、全レコードを過不足なく確認したこと、公式根拠URL、確認日、確認結果または制約理由、適用する短い案内、反映後の内容版を持つ。2026年8月24日時点の丹沢代表施設20件を最初の基準記録とし、交通時刻、山小屋・温泉の営業、料金、駐車場の満車など変動する情報は固定値として保証せず、確認済みの概要と公式情報への導線を提供する。以後の新規施設も初回確認記録を作成してから正本へ追加する。

### 5.3 気象の鮮度と注意表示

気象の鮮度は取得時刻から判定し、端末時刻を注入可能なClockから得る。

| 取得からの経過 | 状態 | 表示・更新 |
| --- | --- | --- |
| 30分以内 | 最新 | キャッシュを表示。手動更新は可能 |
| 30分超1時間以内 | 最新 | 画面表示時に通信可能ならバックグラウンド更新 |
| 1時間超3時間以内 | 更新を推奨 | 取得日時を強調し、通信可能なら更新を試す |
| 3時間超 | 古い情報 | 古いこと、取得日時、公式情報への導線を表示 |
| キャッシュなし・取得失敗 | 未取得 | 推測値を表示せず、再試行と公式情報への導線を表示 |

- 8.2節の1回の更新処理が全試行に失敗した後は、同じ山の次の自動更新を60秒以上空け、画面再描画による連続リクエストを防ぐ。
- WeatherKitの現在から12時間以内の予報風速10m/s以上は「風が強い予報」、15m/s以上は一段強い注意として、値、対象時刻、提供元を表示する。気象庁の平均風速区分は初期値の参考であり、測定条件が同一とは限らないことを前提に安全判定へ使わない。
- 現在から12時間以内の時間別予報を注意表示の評価範囲とする。雷、雪・みぞれ・着氷性降水、または任意の3時間区間で5℃以上の気温低下をWeatherKitから取得できた場合は、事実と対象時間を表示する。取得できない情報を「なし」としない。
- WeatherKitの公式警報は、発表機関名とAppleが提供する詳細リンクを含め、原文の意味を変更しない。
- 注意表示は個別の事実を並べ、合算スコアや登山可否へ変換しない。
- WeatherKitの帰属表示と法的リンクを、Appleの最新要件に従って表示する。

#### 前日の気象サマリー

- WeatherKitのDaily Weather Summaryから取得可能な前日の降水量、降雪量、最高・最低気温を表示する。対象は山頂座標、暦日は地点のタイムゾーンとし、丹沢MVPでは `Asia/Tokyo` を使用する。
- 見出しは「前日の気象サマリー（山頂付近）」とし、「実測」「登山道が乾いている／ぬかるんでいる」「安全／危険」等へ言い換えない。
- 現在・これからの予報を先に表示し、前日サマリーはその下の補助情報とする。対象日、提供元、取得日時を併記する。
- 取得から6時間以内かつ対象日が一致するキャッシュは再利用する。対象日不一致、項目欠損、取得失敗を0mm・0cmへ置き換えない。
- 前日サマリーの要求・変換・キャッシュは現在・予報から独立させ、一方の失敗で他方を非表示にしない。手動更新は両方を試すが、結果を個別状態として反映する。

#### 複数ユーザー対応時の共有キャッシュ

個人利用MVPではネイティブWeatherKitと端末キャッシュを使用し、独自バックエンドを導入しない。App Store公開または複数ユーザー対応へ移行する際は、次の共有キャッシュを追加し、アプリの `MountainWeatherRepository` の取得実装だけを差し替える。UIとDomainはWeatherKit REST API、R2、Workersへ直接依存させない。

```text
山詳細の要求
  → 山ID・検証済み山頂座標で共有キャッシュを確認
  → 正常かつ有効期間内なら同じスナップショットを返す
  → 未作成・期限切れなら同一キーの要求を一つへ集約
  → WeatherKit REST APIを1回取得
  → 検証・正規化した気象JSONを共有保存
  → 各端末は取得日時付きで端末キャッシュ
```

- 全国山頂索引や配布前の山域を一律に定時巡回しない。オンデマンド取得を基本とし、先行更新は正式配布中の山域など明示した対象だけに限定する。
- キャッシュキーは山IDと検証済み山頂座標を含める。近隣山の座標を無断で丸めて同じ予報へまとめず、共有単位の変更は表示上の「山頂付近」と精度を検証してから行う。
- 同じ山への同時要求はsingle-flight方式で一つへまとめる。失敗した応答や検証前データを共有せず、直前の正常値を取得日時・古さ付きで維持する。
- 現在・時間別予報と前日サマリーは、取得失敗を互いに波及させない。前日サマリーは対象日ごとに共有し、対象日不一致を返さない。
- 配信JSONにはschema version、山ID、対象座標・標高、対象時刻、WeatherKit取得時刻、共有キャッシュ公開時刻、提供元、帰属、警報詳細リンクを持たせる。アプリは上限・型・日時・座標を検証してからDomainモデルへ変換する。
- WeatherKit秘密鍵とREST API用トークンはサーバー側Secretだけで扱い、アプリ、リポジトリ、公開オブジェクトへ含めない。Appleの利用条件、帰属、加工・キャッシュ配信条件を移行時に再確認する。
- WeatherKit呼出し数、キャッシュヒット率、取得対象山数、配信基盤の読取り・書込み数、保存量、費用を別々に観測する。個人の山閲覧履歴や正確な位置履歴は分析目的で保存せず、運用指標は山ID単位の集計値に限定する。
- 有効期間と先行更新間隔は、13.4節の鮮度表示と矛盾しない値を実測後に `MountainWeatherPolicy` へ固定する。公開規模を理由に古い情報を「最新」と表示しない。

## 7. 権限・プライバシー設計

| 権限 | 使用目的 | 拒否時の挙動 |
| --- | --- | --- |
| 位置情報（使用中のみ） | 距離・方角表示、カメラ山候補の算出 | 一覧・検索で代替。カメラ候補は使えない。 |
| カメラ | 山候補を映像に重ね、「気になった山」を明示撮影する | 一覧・検索で代替。撮影・記録は利用不可。 |
| モーション・フィットネス | 端末姿勢を使った候補算出 | 候補精度が低下するため、利用不可または限定表示。 |
| 通信 | 気象更新、オフラインパック取得、外部リンク | 保存済みデータのみ表示。 |

- カメラ映像、気になった山の写真、正確な位置履歴、個人メモ、よく使う出発駅をサーバーへ送信しない。気になった山の視点位置は、記録ごとの明示保存時だけ端末内に保持する。登録駅名以外の検索履歴は保存せず、通常ログにも出力しない。
- AI を将来導入する場合は、送信項目と利用目的を個別に示し、明示操作時だけ送信する。
- 個人データ、気になった山の写真、診断ログには `NSFileProtectionComplete`、再取得可能なパック、導入一時領域、気象キャッシュには `NSFileProtectionCompleteUntilFirstUserAuthentication` を適用する。SwiftDataはストア本体、WAL、SHM、格納ディレクトリで保護方針を揃える。
- `UserDefaults` は機密でない設定だけに使用する。将来秘密情報が必要になった場合はKeychainの `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` を使用し、同期しない。
- `PrivacyInfo.xcprivacy` をアプリターゲットへ含め、Required Reason APIの使用と理由を実装変更と同時に更新する。

## 8. 性能・品質の目標

- 山一覧・山詳細（保存済みデータ）は通常操作で約 1 秒以内に表示する。
- カメラ候補はセンサー更新に追従して、体感上遅れなく更新することを目標とする。
- カメラ画面を終了・バックグラウンド移行した際は、カメラ・位置・モーションの更新を停止して電池消費を抑える。
- オフライン状態で、丹沢パック内の山候補算出と山詳細の閲覧が可能であること。
- 実地検証では、複数の代表地点で候補の有用性、方位ずれ、誤候補を記録し、候補算出の改善に利用する。
- 丹沢外のARテストパックは正式対応と数えず、基本情報以外の欠損を丹沢パックの品質評価へ混在させない。

## 8.1 カメラ山候補表示の検証・デバッグ設計

現地でしか確認できない要素を最小化するため、候補算出を「端末センサーの取得」と「候補を計算する純粋なロジック」に分離する。後者は現地へ行かずに繰り返し検証できるようにする。

### 現地で行うこと

- 実際の見晴らし地点で、位置・標高・方位・端末姿勢・カメラ画角・各精度値を短い診断ログとして記録する。
- ユーザーが目視で確定した山名と、候補表示の結果・手動補正量を記録する。
- 必要な場合だけ、ラベルを重ねたスクリーンショットまたは参照写真を記録する。カメラ映像の常時保存は行わない。
- 代表地点は丹沢主稜、表尾根、大山周辺に加え、開発用ARテストパックを用意した高尾・陣馬、八ヶ岳、仙丈ヶ岳、男体山、谷川岳等から、天候と移動機会に合わせて選ぶ。近距離・中距離・遠距離、開けた稜線・樹林越し等の条件を分けて記録する。

### 現地以外で行うこと

- 診断ログを読み込む「リプレイモード」を開発用に用意し、記録時と同じ位置・方位・姿勢を入力として候補算出を再実行する。
- 初期の端末内リプレイは、記録時のラベル位置と現在の候補算出によるラベル位置を同一の疑似画角上へ重ね、スライダー、前後移動、自動再生で確認できるようにする。現在の候補は保存済み5Hzサンプルを先頭から時系列に再計算し、ラベル安定化と候補シートの継続状態を復元する。記録されていない中間フレームまでは再現できないことを明示し、カメラ映像がなくても候補算出の差を確認できることを優先する。
- 山頂データ、地形データ、方位補正、画角、候補の順位付けを変更した後、同じリプレイログで結果を比較する。
- 距離・方位・仰角・画角内判定・見通し判定は、固定入力に対する自動テストを作成する。
- Xcodeの位置情報シミュレーションは位置の確認に利用するが、実機のコンパス・姿勢・カメラとの整合は現地ログを正とする。

### 開発用の診断モード

- 通常の利用者向け設定画面には表示せず、開発ビルドまたは明示的な開発者操作時だけ開けるようにする。
- 現在の位置・標高・方位・端末姿勢・ズーム倍率・カメラ画角を確認できるようにする。GPSおよびコンパスの精度、真北補正の有無、利用中のオフラインパックと地形データの範囲も併せて表示する。
- 代表地点（例：塔ノ岳、蛭ヶ岳、大山周辺、および導入済みARテストパックの地点）を選んで、位置・方位・高度・倍率を疑似入力できるようにする。
- 現地で候補表示がずれた場合は、目視で確定した山名と手動補正量を含む診断ログを保存できるようにする。
- AR画面、候補一覧、センサー精度値を一枚にまとめた診断用スクリーンショットを保存・共有できるようにする。
- カメラ映像や位置履歴を常時保存しない。診断記録は利用者が明示的に開始・保存したものだけを保持する。

### 合格記録（ゴールデンデータ）

- 実地で確認した地点ごとに「この方位・姿勢では蛭ヶ岳が上位候補に含まれる」などの期待結果を保存する。
- 修正後に、既存の地点で候補が悪化していないかを自動比較する。
- 現地で見つかった誤候補は、必ずリプレイ可能な再現データとして追加する。

この運用により、実地登山はデータ収集と最終確認に集中し、日常の開発では再現ログを使って候補計算を改善できる。

## 8.2 異常系・エラー処理方針

### 共通原則

- 取得できない情報を正常な値のように見せない。「不明」「未取得」「更新できません」「データが古い」を状態と理由、最終取得日時とともに明示する。
- 山名のAR表示は候補であり、精度が低い場合は断定的に表示しない。候補の確信度を下げ、手動選択・手動補正へ誘導する。
- 一部の機能が利用できなくても、検索・一覧・保存済みのオフライン情報など、利用可能な機能へ安全に切り替える。
- 障害の内容、復旧手順、設定画面または再試行への導線を短く分かりやすく提示する。

| 分類 | 想定する異常 | 表示・復旧の方針 |
| --- | --- | --- |
| 位置情報 | GPSが取得できない、精度が低い | 精度低下をAR画面に表示し、候補の断定を避ける。現在地を使わない検索・一覧は継続する。 |
| 方位・姿勢 | 磁気干渉、コンパス精度低下、端末姿勢の不安定 | 補正案内を表示し、必要に応じてARラベルを参考表示へ下げる。手動補正を利用できるようにする。 |
| カメラ | 権限未許可、利用不可、起動失敗 | 設定アプリへの導線を示す。カメラを使わない方角リスト／山詳細へ切り替える。 |
| オフラインパック | 対象地域が未導入、破損、更新が必要 | 必要なパック名、容量、更新日を表示する。通信可能時にダウンロード・再取得を案内し、既存パックを自動削除しない。 |
| 端末容量・ダウンロード | 空き容量不足、ダウンロード中断、ファイル検証失敗 | 必要容量と空き容量を示し、パック管理画面で利用者が削除・再試行できるようにする。 |
| ネットワーク・天気 | 圏外、API障害、タイムアウト、更新失敗 | 保存済みの値には取得日時を付けて表示する。最新値を取得できない場合は「不明」または「未更新」とし、再試行を提供する。 |
| 前日気象 | 対象日不一致、日別サマリー未提供、一部項目欠損 | 現在・予報は維持する。対象日が一致するキャッシュだけを日時付きで表示し、欠損を0へ置換しない。 |
| 出発駅・外部地図 | 登録駅名が空、登録駅なし、地図アプリを開けない | 空の名称は保存せず、登録導線、現在地または別の地図アプリ、目的地情報の閲覧を提供する。 |
| 施設・山データ | 情報不備、営業情報の古さ、参照先の無効化 | データの出典と更新日を表示し、公式リンクへ誘導する。誤りの報告を受け付ける導線は将来拡張とする。 |
| AR候補算出 | 稜線の重なり、遮蔽物、地形データ範囲外、算出失敗 | 表示可能な候補だけを提示し、該当なし・精度低下を明示する。候補の検索・手動選択へ切り替える。 |
| アプリ内部障害 | 想定外データ、処理失敗、クラッシュ | 次回起動時に安全に復帰する。明示的に保存した診断ログだけを用い、開発用診断モードで再現・調査できるようにする。 |

### エラー分類とUIへの変換

Domain／Infrastructureのエラーは、事前決定事項13.6節に従って「一時的な失敗」「利用者の操作が必要」「データ不正」「機能制限」「内部不具合」へ分類する。`AppError` は少なくとも分類、処理種別、再試行可否、内部原因を保持する。表示文言そのものを下位層へ持たせず、Feature境界で次を含む画面状態へ変換する。

- 利用者に分かる短い理由。
- 現在も利用できる機能または保存済み情報。
- 再試行、設定、パック管理、検索等の次の操作。
- 古いデータを表示する場合は、その取得・確認日時。

同じエラーを複数画面で別の意味に解釈しない一方、常にモーダル警告にせず、機能の範囲に応じてインライン状態、カード、アラートを使い分ける。

### タイムアウトと再試行

| 対象 | タイムアウト | 自動再試行 |
| --- | --- | --- |
| WeatherKit／将来の気象共有キャッシュ | 1回15秒 | 一時的な失敗だけ2秒後に1回。全失敗後の自動更新は同じ山で60秒空ける。共有キャッシュでは同一キーの同時要求も一つへまとめる |
| manifest等の小さいHTTP要求 | 1回15秒 | 一時的な通信失敗と5xx相当だけ2秒後に1回 |
| パック本体 | 無通信30秒、処理全体2時間 | Background URLSessionによる中断位置からの再開。先頭からの自動再取得は繰り返さない |

- 値は `NetworkPolicy` 等の一つの設定値型へ集約し、テストではClockと待機処理を差し替える。
- 同一資源の実行中要求は一つへまとめる。画面再描画や連打で重複Taskを作らず、画面離脱時は不要な要求をキャンセルする。
- 権限拒否、容量不足、明示キャンセル、署名・ハッシュ不一致、未知の鍵、未対応schema、SQLite破損は自動再試行しない。
- 署名・整合性エラーをネットワークエラーへ丸めない。再取得する場合も利用者の明示操作を必要とする。

### クラッシュ・保存障害からの復旧

- パック導入ジャーナルに `downloading`、`verifying`、`readyToInstall` を記録する。現在パックの参照は再検証済みの `readyToInstall` からだけアトミックに切り替える。
- 起動時に有効なBackground URLSession taskと一時領域を照合する。孤立した `readyToInstall` は再検証して導入し、それ以外の孤立領域は24時間後に削除する。
- SwiftDataストアを開けない場合、ストア、WAL、SHMを自動削除・上書きしない。個人データ機能を利用不可状態にし、読み取り専用の山一覧・検索・詳細は継続する。
- 個人データ初期化は通常の自動復旧として実装しない。将来提供する場合も、対象と影響を示す独立した明示操作、確認、利用可能なら退避を必要とする。

### 通信と信頼できない入力

- App Transport Securityの標準設定を維持し、HTTPS以外の通信、`NSAllowsArbitraryLoads`、例外ドメイン、独自の証明書信頼処理を追加しない。MVPでは証明書ピンニングを行わない。
- 任意URLをWebViewへ読み込まない。公式リンクは `https`、ユーザー情報なし、2,048文字以下を確認して外部ブラウザまたは利用可能なChromeへ渡す。地図は許可したApple／Google MapsのAPI・スキームだけを型安全に構築する。
- manifestは256KiB以下、署名は64byte、v1は2ファイル、総量は1,000,000,000byte以下（UI表示は1GB）とする。宣言値を超えた受信、未知のファイル、絶対パス、`..` を拒否する。
- SQLiteは読み取り専用、拡張読み込み無効で使用し、コンテンツ由来のSQLを実行しない。地形タイルは展開後131,072byteであること、offsetとlengthがオーバーフローせずファイル内に収まることを検証する。

### 診断ログのライフサイクル

- 診断記録は初期状態で無効とし、明示操作で開始・保存する。未保存の観測値はセッション終了時に破棄する。
- Debugビルドでは5Hz、直前10秒のメモリ内循環バッファ、1ログ最大1,500サンプル（最大5分）を初期値とする。上限到達後は追記せず、保存または破棄を選べる状態にする。
- 保存場所はバックアップ対象外かつ `NSFileProtectionComplete` とする。保持指定していないログの保存上限は30日または20件の早い方で、削除予定を表示する。保持指定したログは自動削除しない。
- 個別削除と全削除を提供する。通常ログ、分析SDK、クラッシュ送信から診断ログを参照・送信しない。
- 共有の既定は匿名化サマリーとする。正確な座標を含むリプレイ用ログは、内容プレビューと追加確認の後だけ書き出す。メモ本文、検索履歴、カメラ映像は自動で含めない。
- 共有用一時ファイルは共有完了・キャンセル後に削除し、残存した場合も次回起動時または24時間以内に削除する。

### Privacy Manifest

- Xcodeプロジェクト作成時に有効な `PrivacyInfo.xcprivacy` をアプリターゲットへ追加する。
- Required Reason APIを使う変更では、Appleの現行一覧、許可理由、YamaLensでの実用途を確認し、同じ変更でmanifestとテスト・レビュー記録を更新する。
- App Store公開前にXcodeのPrivacy Report、App Store Connectの回答、公開プライバシーポリシーを実際の通信・保存・SDK構成と照合する。追跡機能と追跡ドメインは追加しない。

### 安全に関する境界

- 天気、日没、山小屋・アクセス情報が不足・古い場合でも、登山の可否や安全性を結論付けない。
- 注意が必要な状態は表示しても、公式情報の確認を促す補助情報にとどめる。

## 8.3 テスト方針

テストは、速く原因を特定しやすいものを多く、実環境に近く実行コストが高いものを少なくするテストピラミッドとする。

| 種類 | 主な対象 | 手段 | 実行方針 |
| --- | --- | --- | --- |
| ユニットテスト | Domainの計算、検索、季節紹介、鮮度、パック検証、ScreenModelの状態遷移 | Swift Testing | 変更中と引き渡し前に実行する。最も多く用意する。 |
| 結合テスト | Repositoryの具象実装、SwiftData／SQLite、ファイル置換、データ変換 | Swift Testingと一時保存領域 | 関係する変更時と引き渡し前に実行する。 |
| UI操作テスト | 一覧→検索→詳細、お気に入り、メモ、気になった山の撮影・保存・削除、保存済み情報等の重要導線 | XCTest／XCUIAutomation | 主要導線に限定し、引き渡し前に実行する。 |
| 性能テスト | 候補順位付け、パック読み込み等の性能上重要な処理 | XCTestの計測機能 | 実装後に基準値を記録し、該当処理の変更時に比較する。 |
| 実機・現地検証 | カメラ、真北方位、姿勢、画角、権限、WeatherKit、地図アプリ、実際に見える山 | iPhone 15 Pro以降の実機、ARテストパックを用意した複数山域、初期正式対応確認時の丹沢代表地点 | 自動テストと区別して記録し、未実施なら該当する完了条件を満たした扱いにしない。 |

- 自動テストは現在時刻、実ネットワーク、現在地、実センサーへ依存させず、Clock、Repository、センサー観測値、保存先を固定入力へ置き換える。
- 候補算出では、北の0度境界、画角境界、低精度、同順位、ズーム、手動補正、範囲外データをパラメーター化して検証する。
- オフラインパック、個人データ、気になった山の写真、天気キャッシュは、一時ファイルまたはメモリ内ストアを使って実際の読み書きとロールバックを検証する。気になった山は、候補未選択時に撮影できないこと、明示保存なしに写真・視点位置を残さないこと、記録削除で関連ファイルも削除することを検証する。
- 季節紹介は固定したClockで、中心期間、前後の紹介期間、年またぎ、該当なし、同点時の安定順を検証する。詳細パック未導入・通信なし・位置情報未許可でも同梱データから表示できること、近い山が0件なら検索導線を返すことを検証する。
- UIプレビューは状態の目視確認に使用するが、単独では受け入れ条件の自動テスト証拠としない。
- コードカバレッジは未検証箇所を見つける補助指標とし、MVP開始時に一律の達成率を設けない。重要な分岐と受け入れ条件を検証した事実を優先する。
- バグ修正では、修正前に失敗する最小の回帰テストを追加してから実装修正する。
- 詳細な選定、配置、固定データ、実行順序、証拠の規則は `.agents/skills/develop-yamalens/references/testing-strategy.md` に従う。

## 9. 実装順序

1. 丹沢の最小山データ（山頂、名称、別名、座標、標高、今の時期の紹介用季節メタデータ）を端末内へ読み込む。
2. 山一覧・検索・山詳細の骨組みと、メモ・お気に入りの保存を実装する。
3. 現在地から距離・方角を算出し、詳細画面へ表示する。
4. カメラ、方位、端末姿勢を取得し、カメラ画面で方位線・候補一覧を表示する。
5. カメラ画角と仰角を使った候補の重ね表示を実装する。
6. 山頂・DEM・出典だけを持つ開発用ARテストパックを、訪問可能性と天候に合わせて丹沢外の山域にも生成できるようにする。
7. Debugの通常起動では6山域のパック管理を集約し、一度の操作で不足パックだけを導入する。カメラ候補は各SQLiteカタログの和集合とし、DEMリゾルバーは現在地を含む詳細範囲のうち中心が最も近い1パックへ委譲する。山域別起動引数では従来どおり単一パックへ固定できる。
7. トラックAとして、地形データの見通し判定、現在・予報・前日サマリーの気象取得、山小屋・交通等、オフラインパック更新、よく使う出発駅、公式リンク・地図アプリへのアクセス導線を自宅で並行して整備する。
8. トラックBとして、晴天と訪問機会が得られた山域でオフライン実地検証し、診断ログを固定リプレイへ追加して誤候補と精度低下時の表示を改善する。トラックBの待機を理由にトラックAを停止しない。
9. 初期正式対応の完了前に、丹沢の代表地点を少なくとも1地点含む現地ログで最終確認する。

## 10. 残るデータ整備と実測

技術方式と初期パラメーターは決定済みである。次は実データと実機で次を確定・調整する。

1. 丹沢パックに最初に含める山、登山口、山小屋、施設のレコード一覧を作成する。
2. 採用する国土地理院データセットごとに、利用条件、測量法上の手続、出典・加工表示を確認する。
3. 5〜10m、50〜250mの地形データを試作し、容量、読み込み時間、見通し判定への効果を測定する。
4. WeatherKitの丹沢山頂座標で、雷、降雪、警報、Daily Weather Summaryを含む取得可能項目と実機認証を確認する。
5. 複数山域の代表地点からゴールデンデータを作成し、事前決定事項13.5節の初期値を調整する。丹沢以外の結果だけで丹沢正式対応の精度を保証せず、最終確認には丹沢の代表地点を含める。
6. JR・私鉄・地下鉄を含む登録駅名をApple Maps／Google Mapsの出発地検索語として渡し、目的地までの経路を開けることを実機確認する。

## 10.1 将来拡張: 登山前チェックと周辺機能

以下はMVPの完成後に追加する。AIの利用を前提にしない。

### 登山前チェック

- 山詳細の上部に、登山準備の確認状態をまとめたカードを表示する。
- 項目は「オフラインパック保存」「気象の最終取得時刻」「風・警報等の注意」「日没」「山小屋の公式情報」「登山口までの経路確認」を基本とする。
- 各項目の状態は `確認済み`、`注意`、`未確認`、`情報なし` のいずれかとする。
- 地図アプリまたは公式サイトをYamaLensから開いた後、該当項目をユーザーが確認済みにできる。
- この機能は確認漏れ防止のためのものであり、登山可否や安全性を自動判定しない。

### AR表示付き写真の保存・共有

- MVPの「気になった山」のアプリ専用写真とは別に、ユーザーがカメラ画面で明示的に実行した場合だけ、山名・標高・距離・方角を重ねた画像をフォトライブラリへ保存または共有する。
- 保存先と、重ねるラベルを確認・非表示にできるようにする。写真ライブラリ権限と共有先への送信は、この将来機能を有効にした時だけ扱う。

### 登山予定日と前日確認

- 山、予定日、任意メモを登録できる。
- 前日には、保存済みパック、最新気象、日没、アクセス確認の状態を確認する画面を提示する。
- 通知はUserNotificationsによる端末内ローカル通知だけを使い、独自サーバー、APNsによるリモート通知、位置連動通知を使用しない。
- 通知は既定OFFとする。ユーザーが最初の予定で「前日に通知」を有効化した直後に、用途を説明して通知権限を要求する。初回起動では要求しない。
- 初期時刻は予定日前日の18時とし、変更可能にする。予定日・通知時刻の変更では同じ識別子の予約を更新し、予定削除・通知OFFでは予約を取消する。
- ロック画面へ予定を過度に露出しないよう、既定本文は「予定している山の情報を確認してください」とし、通知タップで対象の山詳細へ遷移する。
- 通知作成時点の気象値を本文へ埋め込まず、タップ後に山詳細で更新を試す。通知の配信時刻は保証せず、緊急警報、安全機能、気象更新通知として扱わない。
- 権限拒否・取消時も予定と前日確認画面は利用でき、設定画面への導線だけを表示する。通知権限を繰り返し要求しない。

### お気に入り山の更新表示

- お気に入り一覧で、前回閲覧後に気象キャッシュ、オフラインパック、または公式情報の確認日が更新された山へ更新バッジを表示する。
- 更新内容の詳細は山詳細画面で確認できる。

## 11. MVPのデータ取得元と技術要素（採用方針）

### 11.1 採用するデータ取得方針

| 情報 | MVPでの取得元・方法 | 端末での扱い | 方針 |
| --- | --- | --- | --- |
| 山頂の名称・座標・標高・別名 | 丹沢向けに整備する `Mountain` データ。国土地理院の地図・公開地理情報で照合する | オフラインパックへ常時保存 | 山候補算出の基礎データ。外部 API へのリアルタイム照会はしない。 |
| 地形・標高 | 国土地理院の基盤地図情報数値標高モデル。DEM5A、DEM5B、DEM5C、DEM10Bの順に採用 | 解像度を調整してオフラインパックへ保存 | 山頂までの仰角、必要に応じた見通し判定に使う。DEM1AはMVP対象外。アプリ内に出典と加工表示を行う。 |
| 山小屋・登山口・駐車場・温泉 | 公式サイト、公開API、RSS等。基本情報は初回に人が確認し、承認済み情報源の変動項目だけを低頻度で自動取得 | 基本項目・公式 URL・最終確認日または取得日時を保存 | 網羅的・汎用的なスクレイピングは行わない。変わりやすい詳細は古さを明示し、公式ページへ誘導する。 |
| バス・ロープウェイ等 | 各事業者の公式サイト、公開API、GTFS等 | URL と最終確認日または取得日時を保存 | 構造化データを優先する。承認済みサイトだけに専用抽出規則を設け、リアルタイム運行を保証せず公式ページを開けるようにする。 |
| 気象 | 個人利用MVPはWeatherKitのネイティブSwift API。複数ユーザー対応時はWeatherKit REST APIと共有キャッシュ | 端末キャッシュ。将来は検証済み気象JSONをオフラインパックと分離して共有保存 | 現在、時間別・日別予報と前日のDaily Weather Summaryを取得する。公開規模でも全国全山を定時巡回せず、閲覧された山を中心に重複取得を抑える。データ提供元表示を行う。 |
| 外部経路 | Apple Maps、Google Maps | 登録駅はSwiftData、経路は外部アプリ | 利用者が入力した登録駅名を出発地検索語として、現在地または登録駅と目的地を外部地図へ渡す。経路計算は行わない。 |
| 警報・防災情報 | 気象庁の公式情報へのリンクから開始 | URL を保存 | MVPは独自解析せず、公式情報を直接確認できるようにする。XMLデータ連携は後続検討。 |
| 日の出・日の入り | 端末内の天文計算 | 計算結果を表示 | APIを使わず、山頂座標・日付・タイムゾーンから算出する。 |

OpenStreetMap は施設候補を調べるための補助データとして利用できるが、MVPの配布データの主ソースにはしない。採用する場合は ODbL の帰属表示・派生データに関する条件を別途確認する。

`Data/SourceManifests/` の各YAMLは、少なくとも `id`、提供者、データセット名、取得元URL、利用条件URL、取得日、元データ更新日、利用条件確認日、対象範囲、入力ファイルSHA-256、加工手順、アプリ表示用出典、測量法等の手続確認結果を持つ。自動取得する情報源では、これに `robots.txt` の確認結果、再利用条件、取得頻度、許可する抽出項目、取得方法、抽出規則の版を加える。値が未確認のまま配布パックを生成せず、パックの `sourceManifestIDs` から使用した記録を追跡できるようにする。

施設情報の自動取得はパック作成ツールの前処理として実行し、アプリは各公式サイトを巡回しない。API、RSS、GTFS、JSON-LD等を優先し、HTMLしかない場合だけ承認済み情報源専用の抽出処理を使用する。取得頻度は情報源の更新頻度と利用条件に合わせ、通常は登山シーズン前および低頻度の定期バッチとする。新規情報源、抽出規則の変更、大幅な差分、曖昧な営業・通行情報は人の確認対象とし、通常の未変更データを毎回全件確認しない。取得・検証に失敗した値は公開候補へ上書きせず、直前の正常な値とその確認日を維持する。

### 11.3 山候補算出の最小アルゴリズム

通信なしで次の処理を端末内で実行する。

1. GPSから現在地・標高・精度を取得する。
2. Core Location と Core Motion から、真北基準の方位と端末の傾きを取得する。
3. 保存済みの山頂ごとに、距離、方位、仰角を計算する。
4. カメラの水平・垂直画角内にある山を抽出する。
5. 方位・仰角の差と、位置・方位精度を使って順位付けする。
6. 地形データがある場合のみ見通し判定を行い、候補を再順位付けする。
7. 上位候補をカメラ画面に「候補」として重ねて表示し、ユーザーが山名を選択する。

### 11.4 今は採用しないもの

- 写真をクラウドへ送る画像認識 API。
- AI APIによる登山前チェック。
- 承認されていない情報源に対する汎用的・無差別な自動スクレイピング。
- アプリ実行中に端末から施設サイトを直接巡回する処理。
- OSM／Overpass APIのアプリ利用中のリアルタイム照会。
- 個人利用MVPでの独自バックエンドサーバー。複数ユーザー対応時の気象共有キャッシュは、利用枠と運用負荷を実測してから限定的に追加できる。

MVPの中核となる山の閲覧は端末内データだけでも成立させる。オンライン処理はWeatherKitによる気象取得、立ち寄り検索地点のMapKitによる一時解決、外部地図への経路検索、オフラインパックの取得に限定する。個人利用MVPではR2の静的ファイル配信を使用し、ユーザーアカウントや独自サーバーを導入しない。複数ユーザー対応時は、全山巡回を避けるための気象共有キャッシュだけを最小のサーバー機能として先に検討し、個人データ同期や汎用APIへ拡張しない。
